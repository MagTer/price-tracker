## Project

**Price Tracker** — standalone Swedish grocery and pharmacy price tracker, originally extracted from the `ai-agent-platform` monolith at `/home/magnus/dev/ai-agent-platform`. Tracks prices at ICA, Willys, Apotea, Med24, Doz, Kronans Apotek, Apohem, Rusta, Clas Ohlson, and Lyko; exposes its capabilities to the agent platform via an MCP server. Single-**owner**: one admin (Magnus) who may change anything, and read-only access for everyone else the Entra gate authenticates (v0.29.0 — → Auth bullet); one tenant of data either way. Entra ID is enforced at the upstream Traefik + auth-middleware ingress (managed via Dokploy), not inside this app.

**Status (2026-08-13): the extraction is done and this is a live product.** It is deployed in prod. Phase 04.1 — package data moved from `Product` to `ProductStore` — is built, verified, and deployed. Test suite: **857 passing** (that total includes 81 Postgres integration tests; with no DB reachable they skip cleanly and you get `776 passed, 81 skipped`). A number here rots exactly like a pinned version does — the authority is the last green CI run (`gh run view "$(gh run list --workflow=ci.yml --limit=1 --json databaseId -q '.[0].databaseId')" --log | grep passed`), which prints both figures. Enrichment now logs `Enrichment answered with <model>`. **Enrichment can never change the price** — `price_sek` is not in `_ENRICHABLE_FIELDS` and only `None` fields are filled — so that sequence is normal and the JSON-LD price stands. **And it can no longer invent an inverted offer (v0.32.1):** an enriched or LLM-extracted `offer_price_sek >= price_sek` is refused together with its type/details, because a model reading a multi-buy ("2 för 130 kr") reports the bundle price as the per-unit offer.
- **v0.27.0 — watches became editable:** `PUT /watches/{id}` had no dialog behind it, and its `if value is not None` guards made every target a one-way door — settable, never removable. The endpoint now keys on `model_fields_set`, so a **sent null clears** while an absent key is still left alone; the dialog sends every field on save. Both targets are exposed, because the scheduler alerts on `target_price_sek` AND `unit_price_target_sek` and showing only one leaves an invisible trigger on a watch restored from a backup.

**The 04.1 shape — a product is abstract, a link is concrete:**

- **`package_size` + `package_quantity` live on `ProductStore`** (the link), not on `Product`. `unit` (st/liter/kg) stays on `Product`. The product is the abstract thing you compare; the link is the specific package a specific store sells.
- **`PricePoint.unit_price_sek` is GONE.** kr/unit is **computed on read** from `price / link.package_quantity`, exposed as the hybrid `PricePoint.computed_unit_price_sek` (Python + SQL modes). **The single definition lives in `src/domain/pricing.py`. Do not write a second one anywhere.** Correcting a link's amount retroactively fixes all its history — that's the point.
- **`PricePoint.store_unit_price_sek`** is the store's *printed* comparison price. It is displayed beside the computed value and **never sorted on** — stores print in different units, so sorting on it compares kr/kg against kr/st.
- **`ProductStore.scraped_package_quantity`** is what the page said, kept as *evidence*. Typed input is *intent*. Evidence autofills an empty field and **flags** a conflict; it never overwrites intent.
- **A campaign is ORDINARIE + OFFER, identically in every store (v0.25.2–v0.25.3):** `price_sek` is the ordinarie price, `offer_price_sek` is what you pay now, `offer_type="kampanj"`. Both extractors used to be wrong, in opposite directions. **Willys API (corrected again in v0.41.1):** `priceValue` is ordinarie and **the per-unit campaign price is `potentialPromotions[].price.value`** — `savingsAmount` is the TOTAL saving over the promotion's `qualifyingCount`, NOT a per-unit discount. v0.25.2's `priceValue - savingsAmount` rule was verified on a single-unit campaign (21.29 − 3.39 = 17.90 = `price.value`), where the two coincide — on a multi-buy it invented a price that exists nowhere (Bryggkaffe, 2026-07-29: ordinarie 67.90, "Välj & blanda! 2 för 99,00", savingsAmount 36.8 = 2×67.90 − 99; the subtraction recorded 31.10 while the shelf charges 49.50/st, and 31.10 ranked as an absurd bargain in every kr/unit view). The subtraction survives only as the fallback for a saving with no promotion price **and no multi-buy in sight (v0.41.2)**: any promotion with `qualifyingCount > 1` refuses the fallback wholesale — a multi-buy whose promotion price is missing or unparseable gets NO offer, never a guess — and a `price.value` arriving as a string is parsed rather than silently demoted to that arithmetic. `offer_details` carries the store's own `cartLabel` ("Välj & blanda! 2 för 99,00") so the multi-buy CONDITION is visible — **in the portal's price cell too, not just the email (v0.41.2)** — and a promo price with no label gets NO details ("Spara 36,80 kr" beside a per-unit price would claim the TOTAL saving per unit); promo prices are quantized to öre ("3 för 95" arrives as 31.666…), several priced promotions pick the HIGHEST (smaller claimed saving is the safer error, Lyko's rule), and an offer at or above ordinarie is refused wholesale (v0.32.1). The even earlier code ADDED the saving, inventing a "regular" price that appears nowhere in the API. NB the `/erbjudanden/offline-*` pages are NOT product pages — they are butiksblad offers served from `/axfood/rest/v1/offline-product/{storeId}/{code}` (store-scoped, "olika sorter", jfr-pris as a RANGE) and are not trackable links. **JSON-LD pharmacies:** the struck-through ordinarie hides in the offer's `priceSpecification` — `ListPrice` (Apohem) or `StrikethroughPrice` (Kronans), dict or list, http or https — and counts only when it is **higher** than `offers.price`; the old code kept the current price as `price_sek` and discarded ordinarie, so a pharmacy sale never surfaced in "Erbjudanden". A `UnitPriceSpecification` bearing only the jfr-pris is not an ordinarie. **kr/unit is unaffected by all of this** — it ranks on `effective_price_sek = coalesce(offer, price)`, which is the price paid either way.
- **`ProductStore.store_label` (v0.6.0)** is the link's optional display store name ("ICA Maxi Sandviken") for chains that price per physical butik — two ICA butiker are two links under the ONE chain-level `Store` row (whose slug drives the extractors; never add per-butik Store rows). `domain.models.link_store_name` (label wins, chain name is fallback) is the single display rule; every store-name emission (links, history, deals, emails, MCP) goes through it. Quick-add suggests the label from the URL's `/stores/<id>/` segment (`quickadd.KNOWN_STORE_LABELS`), and for butiker in `quickadd.SIBLING_STORE_GROUPS` it also offers to create the sister-butik links in the same confirm (v0.7.0) — siblings are created optimistically and left for the scheduler (v0.19.0 stopped fetching them inline: sister butiker share ONE `store_id`/host, so an inline check per sibling was the same-host burst that tripped ICA's WAF, and under the block-aware fetcher a rate-limited fetch is indistinguishable from an absent page, so it would wrongly delete valid siblings). Both tables are per-instance operator config since v0.8.0: env `QUICKADD_STORE_LABELS` / `QUICKADD_SIBLING_GROUPS` (JSON), in-repo defaults are Magnus's butiker, malformed JSON warns and falls back — the repo is public/MIT and a second instance sets its own.
- **The check schedule is a STORE property (v0.13.0):** `Store.check_weekdays` (JSONB list, 0=måndag — ICA `[0]`, Willys `[0, 4]`) + `Store.check_frequency_hours` (72 for the pharmacies), both modes morning-aligned (06–12 — **Europe/Stockholm wall-clock since v0.33.0**: the window and the weekday are computed in `STORE_TIMEZONE` and converted back to the app-wide naive-UTC storage convention, because "förmiddag" and "måndag" are Swedish civil concepts; computed directly on UTC they silently meant 08–14 Swedish summer time, drifted an hour at each DST change, and would judge a check at 00:30 Swedish Monday night as Sunday's. **Instants stay naive UTC everywhere — only the civil-rule computation and the UI's `parseUtc` display layer are timezone-aware; never store local time**). A link's own `check_weekdays`/`check_frequency_hours` are NULL in the normal state = inherit; setting either overrides WHOLESALE. Resolution + next-check time live in `domain/schedule.py` — one definition, used by the scheduler and the admin `/frequency` endpoint alike (its private copy was removed; do not reintroduce one); **since v0.39.0 both resolve through `next_check_time_for_link`, which STRATIFIES the förmiddag slot**: `weekday_slot` (also in `schedule.py` — THE sibling lookup, never copy its query) ranks the link among the store's active links landing on the same weekday and places link *i* of *n* at `start + (i + 0.5) × window/n` ±25 % of a stratum, at second resolution. The old free draw (independent random hour/minute, `second=0` — 360 whole-minute slots) was uniform in expectation but lumpy in practice: prod had 4 pairs of ICA links on the exact same minute (expected — birthday math), and same-minute due times drain through the rate limiter back to back, the burst pattern that walls ICA. Interval mode and retries keep the free draw — no sibling set to stratify over. Quick-add and the add-link dialog ask nothing about scheduling; only the link-edit dialog offers the override.

- **ICA's Monday prices are live shortly after MIDNIGHT, not in the morning — measured, unharvested until 2026-08-14, and still an OPEN lever.** A one-off cron probe ran outside this repo (`~/ica-natprobe/` on the dev box: `probe.py`, `results.jsonl`, `RESULTAT.md`) across the night of 2–3 August 2026 to answer one binary question — does ICA flip prices in a midnight batch or by hand in the morning? Four products at two ICA butiker, six runs. **Bregott Maxi went 39,90 → 48,95 somewhere between Sun 22:30 and Mon 00:15 Swedish**, and nothing moved after that through 06:00. So Monday's shelf is already true by ~00:15, while `check_weekdays = [0]` + the 06–12 window means a link can be checked as late as noon: the buy list a reader opens at breakfast may still hold Sunday's prices, and the Monday email fires at 12:00 by construction. **Moving ICA's window earlier is therefore a real, evidence-backed option — and it is NOT taken here**, because the evidence has limits worth stating before anyone acts on it: exactly ONE of four products moved (n=1 week), the move observed was a campaign ENDING (price UP), which does not prove a new campaign APPEARS at the same moment, and one 03:00 run came back 404 on a product that answered fine at 06:00 — night traffic may meet a different wall than daytime traffic does. Also note the probe itself is the honest way to settle it: re-run it over more products and more weeks rather than reasoning from this paragraph. **What is recorded here is the measurement, not a schedule change** — the schedule is edited by hand, per the read-only rule in the statistics bullet. Two things from the probe's own README that outlive it: (1) **its stated precondition is already met** — it said moving the window "kräver att schemafönstret görs Europe/Stockholm-medvetet först — det räknas i UTC idag", which v0.33.0 did, so the lever is now a value change rather than a rewrite; and (2) **Willys was already known to flip in 00:11–01:14 on Sunday night** (read off the tracker's own price history, which is why ICA was the open question at all) — a second store batching just after midnight, which is what made the midnight hypothesis worth testing.
- **`Product.category` is a fixed ordered enum (v0.20.0–v0.21.0):** the 10 grocery-section values and their in-store walk order live in `domain/categories.py` (THE list). `normalize_category()` coerces free text / an old LLM guess to a canonical value or None (keyword map; `"ost"`/`"fil"` ordered last so they don't swallow `"kosttillskott"`/`"filmjölk"`); `category_sort_index()` is the aisle-order sort key (ready for a future shopping-list sort; the product list still sorts by name). The UI `<select>` is server-injected from the list in `render_admin` (no second copy) and `test_static_gates.py` guards the `<!--CATEGORY_OPTIONS-->` placeholder. Server normalises on create/update/import. Free text is gone; "Kött, Chark & Deli" merged the old meat/chark/fish split.
- **The politeness ledger is SHARED and lives in `infra/rate_limiter.py` (v0.14.0):** `StoreRateLimiter` (process-wide singleton via `providers.get_rate_limiter`, injected into the scheduler) is THE per-store request throttle — reserve-a-slot, keyed by store id. The scheduler spaces its background checks 60 s apart (`RATE_LIMIT_DELAY`); the **interactive** fetches (quick-add preview, first check, manual re-check in `admin.py`) now go through the SAME ledger with a short interval and a `max_wait` cap (env `QUICKADD_RATE_LIMIT_DELAY`=5 s, `QUICKADD_MAX_WAIT`=10 s) so they can't burst a store's WAF while never stalling a human on a background reservation. **Both cadences carry jitter on top of the floor (v0.24.0)** — `RATE_LIMIT_JITTER`=30 s background, env `QUICKADD_RATE_LIMIT_JITTER`=3 s interactive — so a store isn't hit on a clockwork beat; jitter only extends the *next* slot, never the current caller's wait (`max_wait` still holds). Before the shared ledger, interactive fetches bypassed all throttling — that is what let quick-add + scheduler checks trip ICA into HTTP 202/403. **Do not reintroduce the scheduler's old private `_last_request_at` dict.**
- **The fetcher fails honestly on a bot wall (v0.14.0; hardened v0.25.0):** `WebFetcher.fetch` never treats a wall as a page (the old `raise_for_status()` let a 202 through as an empty page → "metadata extraction failed" instead of "blocked"). **WAF statuses (HTTP 202/403/405/429) FAIL FAST — no retry — and return `blocked=True`:** ICA's 202 is an AWS WAF JS challenge (`awsWafCookieDomainList`/`gokuProps`, needs a real browser to mint an `aws-waf-token`) that a few-second retry cannot solve and only reinforces the IP flag. Only *transient* failures (5xx, network error, empty body) get the short bounded retry (`_RETRY_DELAYS_SECONDS`); a hard 4xx (404/410) fails fast. **405 is a wall, not a method error (v0.29.3, from prod evidence).** ICA answers 405 to a plain GET while it is walling us: we only ever GET, these are pages a browser opens, and the SAME urls returned 200, 405 AND 202 within one morning (Ketchup priced 06:42 → 405 at 10:01; Tortilla priced 09:42 → 405 at 10:03; Kaviar 405 at 07:56 → 202 at 10:13). The 405s arrive in RUNS starting on the first probe after a cooldown lapses. Classified as a hard 4xx it left `blocked=False`, so the breaker never re-tripped and the scheduler fed ICA at its 60-90 s cadence straight through the wall — and each 405 pushed its link +24h out of the förmiddag window. A genuine 404/410 is still a hard error and must NOT cool the store down. The `blocked` flag propagates `fetcher → perform_price_check` (`PriceCheckOutcome.blocked`) `→` **every caller** — scheduler AND the interactive endpoints — into the shared registry (→ store-block bullet). **The fetcher logs at the point of detection (v0.28.0):** a bot wall, a hard 4xx and a give-up-after-retries each get their own WARNING, because a WAF challenge used to produce *no log line at all* and the first evidence was a caller's generic "fetch failed". Fingerprint: consistent Chrome UA + `sec-ch-ua` + `sec-fetch-*` (bump `chrome_major` when stale) **plus HTTP/2 (v0.28.0, `httpx[http2]` → `h2`)** — a client claiming to be Chrome and then speaking HTTP/1.1 to a CDN contradicts itself at the connection layer, before a header is read; verified h2 negotiates against ica.se, willys.se and apotea.se — and **the negotiated protocol is logged once per host per process (v0.28.3)**, INFO for `HTTP/2` and WARNING for a 1.1 downgrade, so prod logs can prove which protocol each store actually got. None of this beats the JS challenge or the TLS/JA3 layer — `curl_cffi` shipped in v0.30.0 for the TLS/h2 half (→ transport bullet); a headless browser remains the un-built lever for the JS challenge itself. **But measure before building either (2026-07-26).** A probe run against the exact URL that had just been walled, 17 minutes after the 202: **plain httpx with these very headers got the full 510 KB product page**, from the same public IP that had just been refused. And the requests around the block were ~2 minutes apart — *slower* than the scheduler's own cadence. So that challenge was neither rate-driven nor fingerprint-driven; it was **sampled**. `curl_cffi` was installed and tried in the same probe (it also got 200) but proved nothing, because the control had already succeeded. **That probe also produced a wrong claim worth not repeating: its `http_version: 3` was read as HTTP/3. In curl's enum 3 is HTTP/2; HTTP/3 is 30.** curl_cffi buys TLS/JA3, h2 SETTINGS and header order — not a protocol upgrade (`_normalise_http_version` in the fetcher now encodes that, with a test). **It was ported anyway in v0.30.0** — not on the strength of the theory, but because the change is small, reversible and finally MEASURABLE (→ transport bullet). A headless browser that mints an `aws-waf-token` and hands it to the cheap fetcher is the only lever that addresses the JS challenge itself; curl_cffi cannot solve one. **That lever was measured, it works, and it was declined anyway — read the waf-token bullet before anyone proposes it again.**

- **A browser-minted `aws-waf-token` gets curl_cffi through ICA's wall — measured 2026-07-29, DECIDED AGAINST 2026-08-13.** The spike CLAUDE.md kept demanding before a headless browser was built has been run, from the dev box (`80.216.252.59` — the SAME public IP as the Dokploy VM, verified, so the flag being tested is prod's own). Provoke a wall, mint a token in Chromium, then alternate bare and token-bearing curl_cffi requests **seconds apart** so the wall is provably still up between them — the interleaving is the whole design, because the 2026-07-26 probe concluded nothing precisely by testing after the wall had lifted. Result, three clean rounds: **bare 202 (2492 B) 3/3, `aws-waf-token` 200 (512 711 B) 3/3.** Four facts a sidecar design must be built on, each measured rather than assumed: (1) **the token is HOST-wide, not per-URL** — one mint on the toalettpapper page opened three other products including one in a *different* ICA butik (store id 1003396 vs 1004503), so one browser run covers all 44 ICA links; (2) **a token is only minted when the challenge is SERVED** — run the browser against an unflagged IP and it gets the page directly with no token to hand over, which means mint-on-demand (trigger on the 202) is the only workable trigger, and pre-warming is not a thing; (3) **the browser MUST override its user agent** — Playwright's default carries `HeadlessChrome`, and ICA answers that with a hard CloudFront 403 and NO challenge, so no token; with an ordinary Chrome UA the challenge is served, solved in JS, and the real product page renders (title check, ~776 KB); (4) **judge the browser on CONTENT, not on the navigation status** — the challenge itself answers 202 and the real page arrives after the reload, so a spike that returns early on `status != 200` reports failure on a success (this one did, on its first pass). Also observed: the wall lifts on its own in **~4–5 minutes**, and the token was still opening the page 9 minutes after minting. **The judgement that follows from all this: the scheduler does not need a token, it needs patience — and it already has it** (breaker + `next_check_at` deferral, and ICA links are weekly anyway). What is actually harmed by a wall is the HUMAN path — a quick-add refused with 503 because the breaker is open, which is what prompted the spike. **And that is the harm that stopped happening, which is why no sidecar was ever built (decided with Magnus 2026-08-13).** `check_attempts` over its whole prod life at that point — 2026-07-27 to 2026-08-13, 395 checks — holds **5 blocked rows, all ICA**: four on 2026-07-29 (the spike's own day, under the burst pattern v0.39.0's stratification then removed) and one on 2026-08-12, whose very next check on the same product succeeded **five minutes later** — the breaker's base cooldown doing exactly its job. **Exactly ONE of the five was on the human path**, the 2026-07-29 quick-add preview that prompted the spike; there has not been another since. A sidecar is a Playwright dependency, a browser in the image and a token cache, standing ready for an event that fires once a fortnight and self-heals in five minutes. **Do not build it on the strength of the measurement above — the measurement says the token works, not that it is needed.** If ICA's walls come back (watch `check_attempts.outcome = 'blocked'`, not the logs), the four facts here are what a design starts from — **and the harness that produced them is still in the repo**: `docs/spikes/spike_handover.py` (does a browser-minted token survive the handover to curl_cffi?) and `docs/spikes/spike_scope.py` (how BROAD and how LONG-LIVED is one token?). They are standalone scripts, not tests — nothing imports them, CI never runs them (`testpaths = ["tests"]`) and Playwright is deliberately not a dependency: each imports it lazily inside the browser step and points `CHROME` at a hardcoded path in the dev box's `~/.cache/ms-playwright/`, so on any other machine that line is the first thing to fix, not evidence that the spike rotted. What they cannot be run without is a genuinely flagged IP — the wall has to be up for the interleaving to prove anything, which is exactly why these numbers were expensive to get and should be re-measured rather than re-derived.
- **The fetch transport is swappable and instrumented (v0.30.0):** `WebFetcher` builds a **curl_cffi** `AsyncSession` (`impersonate="chrome"`) by default and an httpx client when env **`FETCHER_TRANSPORT=httpx`** says so; `fetcher.transport` records which one got built and every protocol **and bot-wall** log line names it (the wall line since v0.30.1 — the transport is the ONE thing `check_attempts` does not record, so during a control week the log is what attributes a wall to a transport; the durable COUNT is the table, see below). curl_cffi closes the half of the fingerprint headers cannot reach — the **TLS ClientHello (JA3)** and the **HTTP/2 SETTINGS/priority frames** — because a client sending Chrome's headers over an OpenSSL-default handshake contradicts itself before a byte of HTTP is read. **It does NOT solve the JS challenge** (no JS engine, so no `aws-waf-token` ever), and its benefit against ICA is **PROVEN as of 2026-08-13, on 18 days of prod evidence.** First datapoint (2026-07-28): the 14 ICA links walled under httpx on Monday morning (405/202 runs) ALL passed under curl_cffi within 24h — same URLs, same IP, same förmiddag window. The env var stays the rollback: one restart flips to httpx. Under curl_cffi the UA/`sec-ch-ua` come from the impersonation profile: **never hand-write them on top**, that re-creates the contradiction (`_CHROME_MAJOR` feeds the httpx path only). A missing or broken native lib degrades to httpx with a WARNING rather than leaving the app with no fetcher at all. `curl-cffi` ships prebuilt abi3 wheels, so the image needs no toolchain; **httpx stays regardless** — OpenRouter and Resend use it, and it is the fallback.
- **The scheduler self-defends against store WAFs (v0.23.0 pause, v0.25.0 breaker):** (1) **Auto-pause** — the add flows (`/quick-add/preview`, `/quick-add`, `POST /products/{id}/stores`) call `scheduler.pause_for(...)`, silencing background checks for a window each add pushes forward (env `SCHEDULER_ADD_PAUSE_MINUTES`=60) so a burst of manual adds can't race the scheduler into a store's WAF; `paused_until` shows in `/scheduler/status` and the portal status box (PAUSAD — parse it with `parseUtc`, it's naive UTC). (2) **Per-store circuit breaker** — see the store-block bullet below; the scheduler is now one of its clients, not its owner. **A failed weekday-scheduled check retries in the NEXT day's förmiddag (v0.39.0 — `schedule.next_morning_retry`, never raw `now+24h` arithmetic in the scheduler: +24h kept the clock time the failure happened at, so a link that 404:ed at 12:01 local retried at 12:01 forever, outside the window and drifting across weekdays; note a permanently dead URL retries every morning until a human deletes it — **and that is the answer, not an open question (closed 2026-08-13)**: `domain/link_health.py` flags it after three straight non-blocked failures, Fel & luckor lists it with the store's own words and a "sidan är borta" hint, and the link is deleted from its edit dialog. A BLOCKED one is not a failed one (v0.29.2):** a wall is the store's state, not the link's failure, so the discovering link is deferred to the breaker's `blocked_until` — the same deferral the skip branch already gave every *other* due link of that store. **Since v0.39.0 those deferrals are STAGGERED, not stamped with one timestamp**: the discoverer takes `blocked_until` itself (the probe when the cooldown lapses) and each further deferral of that store lands at least `RATE_LIMIT_DELAY` plus jitter behind the previous one (per-cycle counter, so repeated cycles against a still-cooled store re-spread from zero instead of marching outward). Identical timestamps meant the whole store came due at once and drained on the ledger's 60 s floor back to back — the exact burst that preceded both ICA walls measured 2026-07-29, a self-reinforcing loop (block → identical timestamps → burst → block), and it left 3 links on the same microsecond in prod. Before that, whichever link happened to sit first in the ASC due queue took a 24h penalty for being first while its siblings resumed in minutes, and since +24h keeps the *clock time the wall happened at*, a link blocked at 23:16 retried at 23:16 the next night, and the night after — permanently outside the 06–12 window `domain/schedule.py` exists to hold it in. That was the only mechanism moving checks out of that window. **A blocked link also no longer sets `last_checked_at`** (we never saw the page), so "Senast kollad" and the portal's freshness line stop reporting a wall as fresh data; a fetch that *reached* the store and yielded no price still counts, because the store answered.
- **The circuit breaker is SHARED and lives in `infra/store_block.py` (v0.28.0):** `StoreBlockRegistry` (process-wide singleton via `providers.get_block_registry`, injected into the scheduler) is THE record of "this store is walling us right now". It answers *whether* we may talk to a store; the ledger answers *how fast*. **Every outgoing store call consults it and reports back** — the scheduler skips a cooled store's due links without fetching (deferring `next_check_at` past the cooldown), and the interactive endpoints (`/quick-add/preview`, `/check/{id}`) refuse with **HTTP 503 + `Retry-After`** and a Swedish "butiken blockerar oss" message. Conversely a block found interactively now silences the scheduler. **The cooldown escalates** — base × 2ⁿ, env `SCHEDULER_STORE_BLOCK_COOLDOWN_MINUTES`=**5 since v0.29.1** (was 30; name kept for compatibility) capped by `STORE_BLOCK_MAX_COOLDOWN_MINUTES`=240 — and **the first page that loads resets the strike count**: the predicate is "reached the store" (`failure_reason != "fetch_failed"` — a fetch that succeeded but yielded no price still counts as "the store answered"), and since v0.28.2 the scheduler and the interactive paths use that SAME predicate (the scheduler briefly keyed on full success, so a store whose page layout broke kept stale strikes and the next real block escalated from the wrong level). A lapsed cooldown clears but the strike count survives, so the probe after a lapse escalates rather than restarting at base. In-memory/single-process like the add-pause; the scheduler's DB-side `next_check_at` deferral survives a restart anyway. `blocked_stores` is in `/scheduler/status` and the portal status box shows **BLOCKERAD** (outranking PAUSAD).

**Pristillfällen is the only judgement in this app about the PAST (v0.55.0).** Everything else asks about now — `deals.verdict` compares a product's links at this moment, `deals.timing` compares a price with the product's own floor. This asks whether the campaign we already showed was actually the cheapest way to buy the product THAT WEEK, which makes it the only feedback the tracker gives on its own advice, and the only place a store's own discount percentage gets an answer ("−22 %, and Willys was still 8 % cheaper per kg"). `domain/stats.product_offer_occasions` is THE walk and **`stats.was_cheapest` is THE comparison**, shared with the per-store "varav faktiskt billigast" counter — a `<` in one and a `<=` in the other would make a number disagree with the rows behind it. Four rules it must keep:

- **The verdict is taken BEFORE the point is folded into the series**, so "elsewhere" means the alternatives as they stood, carried forward from each link's last observation. Points from before the window seed that basis and are not themselves rows: a campaign that ran before the period is not in the period.
- **`was_cheapest` is None, never False, when no other link had a known price.** Calling an unjudgeable campaign "not cheapest" invents a loss out of a gap. The row still appears — dropping it would stop the rows from matching the count above them.
- **INACTIVE links are included, unlike everywhere else in `stats.py`** (decided 2026-08-13). That filter exists so "billigast" cannot name a shelf you may not buy from; this table is history, and the same reasoning makes `deals.observed_spans` count inactive links for the floor. A retired link is flagged in the row, because a row the reader cannot act on should say so.
- **The alternative carries `alternative_seen_at`.** With weekly checks the price a campaign is judged against can be six days old; a row saying "Willys låg 8 % under" without saying when it was last seen claims a precision we do not have — the same honesty as the buy list's "sett fredag 24/7".

Its own endpoint rather than a field on `/stats`: that payload carries one row per product for a page showing all of them, and every product's campaign history hung off it would grow the whole table for a view that reads one product at a time. It takes **`days`**, not weeks, because the modal draws the chart and this table from ONE window (`HISTORY_DAYS`) and a window that differed by a day would put a campaign in one and not the other.

What was genuinely missing was the URL and the back button, which cost about a hundred lines instead of a release, and kept the content that v0.54.0/v0.55.0 had already built and tested. The summary strip carries only things the fetched rows literally contain — a minimum, a maximum, a count, a timestamp — plus **förändring READ off `/stats`** when that payload happens to be loaded and simply omitted when it is not: change over a period is `stats.py`'s definition (carry-forward, a baseline from before the window, an em dash rather than 0,0 % on one observation), and a second one computed in JS would drift from it exactly as Gotcha 4 predicts. Same shape as the deal row reading `verdict` instead of deciding it. **Its span bar is labelled "Prisläge i perioden" on purpose:** this app has three windows that could each be called "spannet" — the deal row's 84-day floor, the statistics period, and the modal's own 90 days — and an unlabelled bar would silently pick one. `buildBestAvailableSeries` is kept though nothing draws it: it is THE honest carry-forward walk across links, and the day an envelope is wanted again it should be reused rather than rewritten.

**Prisutveckling (Statistik until v0.47.0) answers cross-product questions, and `domain/stats.py` is THE definition (v0.36.0).** The page is the bigger sibling of the per-product history modal: what moved, where to shop, what a campaign is worth, and what is blocking a comparison. Four rules make its numbers true, and each of them fails SILENTLY and plausibly if broken:

- **kr/unit is never summed or averaged across products** — milk's kr/l plus cheese's kr/kg is nonsense, the same invariant that keeps `store_unit_price_sek` unsortable. Everything cross-product is a PERCENTAGE against that product's own baseline. That is also why v1 has **no basket index**: an index needs chain-linking to survive a product being added (it is added weekly here), and the per-product table answers the same question without the machinery. Weights ("how much do I buy per month") stay unbuilt and optional — an unweighted view needs no input at all.
- **Store comparison uses a MATCHED basket** — only products at least two stores carry. Over full assortments the number compares what each store happens to SELL, not what it charges. A store with several links for one product competes with its own cheapest pack.
- **Carry forward, never interpolate.** A link checked last Monday holds Monday's price all week — that is what the shelf says. A price observed BEFORE the window is the baseline the period opens at, so narrowing the period cannot empty the table.
- **Absence is not zero.** A product observed once has `change_pct = None` and renders as an em dash: "0,0 %" would be a confident claim about a period we did not watch. Every panel prints what it was computed from, which is why the page needs no "come back in six weeks" gate — it matures on its own.

**The statistics page has no write path, and that is a rule, not an omission (decided 2026-07-28).** Not an auto-tuner, not an "apply this schedule" button. Raising check frequency where prices move most means fetching hardest exactly where the WAF lives, and a wall records no price point — so the product that changes most often would come to look like it had stopped. The loop would eat the measurement it is built on. Weekday and volatility patterns are shown as observations; any schedule change is made by hand in the link dialog. The coverage counts link INTO the Produkter facets rather than repeating the lists there.

**The validator asks whether the tracker still SEES what the stores publish, and `domain/validation.py` is THE judgement (v0.44.0).** Born from the jättefranska miss: every ICA check said "ok" while every ICA campaign was invisible — no error anywhere, plausible prices, wrong answer. Two layers, both built on redundancy already recorded, both read-only like statistics (observe, never act, never touch scheduling):

- **Tier regression** — `EXPECTED_SOURCE` maps each store with a structured best tier (ica→ica_page, rusta→rusta_page, lyko→lyko_page, willys→willys_api) and flags any active link whose LATEST `outcome="ok"` attempt answered from a lower tier: the structured source changed shape and the ladder silently degraded. Judged on ok-attempts only (failures belong to link_health, walls to the breaker; one healthy check clears by construction). **Clas Ohlson is deliberately absent** — its extractor returns None BY DESIGN when the page adds nothing beyond JSON-LD, so "jsonld" is normal there and judging it would be a standing false alarm.
- **Jämförpris contradiction** — the store's printed unit price against `price/package_quantity` on each link's latest point: a disagreement beyond tolerance (1.5 % relative AND 0.10 kr absolute — quantity rounding gives 0.4 % noise, the one real prod error sat at 20 %) means the price or the amount is wrong; it catches both failure classes with stored data. **A link passes when EITHER basis matches** — Willys/ICA print the jämförpris off ORDINARIE but Clas Ohlson prints it off the CAMPAIGN price (both verified on prod 2026-08-03), and modeling which store does which is a maintenance treadmill refusing-either avoids.
- **Surfaces:** `/stats` composes `data_quality` into its payload (the endpoint composes two domain definitions; validation ignores the period filter — quality is about NOW); **since v0.47.0 the findings own a page — Fel & luckor** (→ faults-page bullet), where they sit above the gaps as the tracker's silent failures; the Monday email carries the issues as a ride-along block, **only when non-empty**, and a validator crash mails the buy list without it rather than nothing (telemetry must not kill what it rides in — the check_attempts rule again).

**`check_attempts` is what the stores REFUSED to say (v0.35.0).** `price_points` only ever recorded SUCCESS: a failed check writes nothing, and since v0.29.2 a blocked one does not even touch `last_checked_at` (a wall is not an observation). So "how often does ICA actually answer us" was unanswerable from stored data — the only trace was a WARNING in the in-memory ring buffer, which resets on restart. It shipped **before** the statistics page it exists to feed, because a page can be built whenever and history cannot be backfilled.

- **One row per CHECK, not per HTTP request** (a Willys check makes two requests; what is measured is "did we get a price"), and **a skip is not an attempt** — when the breaker is open the scheduler defers a store's due links without fetching, and a row per deferral would measure the schedule instead of the stores.
- **`CheckAttemptLog` writes in its OWN transaction** (`infra/check_log.py`), and that is the design, not a detail: the interactive endpoints raise their HTTPException on a failed or blocked check *before* they commit, so a row added to the request's session is rolled back — losing precisely the attempts worth having. It also **never raises**: telemetry that can kill a price check trades the data for the thing the data is about.
- **The write lives inside `perform_price_check`**, wrapping the flow so every exit — ok / no_price / fetch_failed / blocked, plus an escaped exception as `error` — is recorded from one place. `attempt_log` defaults to None (recording OFF) because several hundred tests drive the flow with mock sessions, so the default cannot be the enforcement: **an AST gate in `test_static_gates.py` fails the build if any `perform_price_check(...)` call in `src/` omits `attempt_log=`.** The quick-add PREVIEW is the one caller that never reaches the flow (it fetches before a link exists), so it records via `_record_store_outcome(..., log_attempt=True)` — `product_store_id` is nullable for exactly that, and `ON DELETE SET NULL` so removing a link cannot fail on an audit row.
- **`domain.result.extraction_source()` is THE reader of `raw_response["source"]`** — the same `isinstance(raw, dict)` dance had been written three times over a loose JSONB dict where a typo returns None and reads as "the LLM answered". It returns the tier verbatim (`willys_api` / `rusta_page` / `clasohlson_page` / `jsonld` / `llm:<model>` / `unknown`), because *which model* answered is what makes cascade spend readable. The LLM path now stamps itself (it was identifiable only by elimination), and the scheduler gained a `checks_page_state` counter: Rusta and Clas Ohlson checks used to fall through to the else and inflate `checks_llm`, the one number anyone reads to judge what the cascade costs, while those tiers call no model at all.
- **Statistics must NEVER feed back into fetch cadence** (decided with Magnus, 2026-07-28). Not automatically, and not via an "apply" button. Raising frequency where prices move most means fetching hardest exactly where the WAF lives, and a wall records no price point — so the product that changes price most often would come to look like it had stopped changing. The loop would eat the measurement it is built on. The planned statistics page is therefore READ-ONLY by construction: no write endpoints at all, weekday patterns shown as observations, and any schedule change made by hand in the link dialog.

**Fel & luckor owns the whole to-do list, and every count on it opens a list that is ON it (v0.53.1).** The counters used to be a way OUT: "Länkar utan mängd" set a facet on Produkter and navigated there — putting the number on one page and the work on another, while the product table holds no affordance that closes any of it. Now the two counts with a per-row action scroll to their own section (`data-issue-goto`), Produkter lost its **Luckor** chip (a stored `needs_amount` filter is cleared on restore — an invisible filter with no control to switch it off is worse than a stale one), and **"Produkter i bara en butik" became a section, not just a figure**: the products whose price cannot be compared against any other chain, with the chains they have and the ones they lack as chips, and a **+ Länk** button opening the link dialog directly. Two rules make that list worth reading: it keys on **`store_slug`** (the chain) rather than the butik label — /stats counts this by label, so an ICA Maxi + ICA Björksätra product counted as two "butiker" while being comparable nowhere, which is why the counter above it is now derived from THIS list (one number, one list, no drift) — and it **excludes own brands** via `missingFromStore`, the v0.38.0 rule, without which an ICA-branded product sits at the top forever as a gap that can never be closed. Candidate chains are restricted to the product's own `store_type`: a bag of coffee does not "saknar Apotea". The two remaining figures (aldrig kollade, äldsta kontroll) are deliberately NOT clickable — they have no per-row action, and a box that looks pressable and does nothing is worse than a plain figure.

**Fel & luckor separates SILENT errors from gaps, and that separation is the page (v0.47.0).** A gap announces itself — a jfr-pris is missing, a cell is empty. A silent error does not: the check reports `ok`, the price is plausible, and nothing anywhere else in the interface reveals that the figure is wrong. That is precisely the miss that produced `domain/validation.py` (ICA's campaigns invisible for weeks while every check said "ok"), so the silent errors sit at the TOP and in red, before the counters; the gaps keep amber below. It is also the answer to "how do I see a parser failure without digging in the logs": **the log shows EVENTS, this page shows STATE** — a tier regression from Thursday has rolled out of the ring buffer by Monday, while the state stays here until a successful check clears it. Four blocks, all from data the domain already computes: `data_quality.tier_regressions` + `.unit_price_mismatches` (the red band), the four `coverage` counts, `link_health`'s broken links, and the links with no mängd — each of the last with an **inline amount field and Spara**, because sending the reader to a dialog three clicks away is how a six-item list stays a six-item list. The consequence text per tier regression is DERIVED from `expected_source` (`TIER_IMPACT` in the template): `ica_page → jsonld` says nothing to anyone who does not know the codebase. **Nothing here may be dismissible** — no flag is persisted, so a dismiss button would only hide an error that is still running; a successful check from the right tier, or a corrected amount, removes the row by itself. The band's foot ("blockerade hämtningar räknas inte som fel här — en vägg är butikens tillstånd, inte vårt") is load-bearing: without it an ICA wall reads as a breakdown and invites deleting perfectly good links. The sidebar badge counts the SAME rows the page lists, derived from the lists' lengths, and turns red the moment a silent error is among them.

**The portal ranks and filters CLIENT-side, and the endpoints keep their contracts (v0.34.0, rebuilt as "3a" in v0.47.0).** UI decisions that are easy to undo by accident:

- **Att köpa's margin is a PERCENTAGE, it is the ORDER, and since v0.53.1 it is not printed on a best row.** `savings_per_unit_sek / best_alt_unit_price_sek × 100` — kronor per unit cannot be compared between rows (0,62 kr/st against 8,20 kr/kg says nothing about which is the better buy), percent can. It is **not** `discount_percent`, which is the store's framing against its own ordinarie and ranks nothing. It had a column of its own in one draft and then a sentence, and it is now neither: every row under "Värt att köpa" is best by construction, so the sentence restated the heading on every row while competing with the **span bar** to be the row's single score — and it won by sitting first and being biggest, which is the wrong winner (the bar answers the question the reader arrives with: *is this a good price*, not *is this the right shelf*). A list expresses its ranking by being a list. **WORSE and UNKNOWN keep their sentence** — the span bar is the TIME axis and cannot say another link is cheaper right now, and UNKNOWN's names the gap plus its fix. **The butik moved into the meta line** when the sentence went: it used to close that sentence, and it is the way OUT to the store's own page. **The span bar comes FROM THE DEAL ROW** (`lowest_unit_price_sek`/`highest_unit_price_sek`, v0.50.0), never from `/stats`: the bar and the `timing` verdict must read the same 84-day window, and the stats period is whatever the Prisutveckling picker last held — a 4-week pick there once made the bar and the "har varit X billigare" note state opposite things about one row. When `high <= low` NO bar is drawn — a bar without a span would claim a position that does not exist, the same rule `stats.py` follows when it returns `change_pct = None` rather than 0. **The offer's villkor (`offer_details`) sits beside the product name** (v0.53.1), not at the row's foot: it is a condition on the price printed to its right ("2 för 99,00" is not a per-unit price you can walk up and pay), and the foot is the last place a swept row is read. It wraps rather than being shortened to a badge — "Max 2" drops which condition applies.
- **The korgremsa is derived from the rows the list shows, and its store pills ARE the filter.** Pill counts, subtotals, the total and the closing sentence all come from the same array the list renders, so a pill cannot promise a round the list does not hold, and no butik can be missing (which would make its rows unreachable). A pill filters client-side on `store_name` and stands beside the header's scope switch, which is `store_type` on the server — the two compose. With a filter active the heading, the sums and the closing sentence all change, or the strip lies.
- **The scope switch is one state with two controls** (the header segment and Produkter's chips) and survives page changes in `sessionStorage`. It filters Att köpa server-side (`/deals?store_type=`) and Produkter client-side via `/stores`' `store_type` per slug.

- **The two offline paths are one card since v0.52.0, and the split between them is the design.** Both exist because some prices never touch the page the tracker fetches, and both keep discovery human. What differs is what happens after: a **blad offer is a LOOKUP** (store-scoped, week-scoped, "olika sorter", belongs to no link) and is still never persisted, while a **price the reader decides IS their tracked product** is an ordinary observation and becomes a price point. The bridge between them (`notable_links` → the "Notera på …" button) fills the form and stops — it must never write on its own, because attributing an offer to a product is exactly the judgement the LLM ladder is not trusted with either. And it must never offer a link at another store: `notable_links` is filtered on the offer's own `store_slug` for the same reason the manual endpoint records `source: "manual"` — an observation has to keep saying where it came from.

**A price a human observed is an ordinary price point, and that is the whole design (v0.49.0).** Some offers never touch the page the tracker fetches: ICA Björksätra advertises förbokning campaigns on Facebook, and that page is behind a login and a bot sensor exactly like the Willys blad listing — **discovery stays human, by the same decision** (→ v0.46.0). But the OBSERVATION is not a second kind of truth: same link, same package, a known day, a price that really could be paid. So `POST /product-stores/{id}/prices` writes a `PricePoint` with `raw_data = {"source": "manual"}` and nothing else is invented — **and note the contrast with a blad offer, which is store-scoped and belongs to no link, and therefore is still never persisted.** Three deliberate omissions: **`last_checked_at` is untouched** (we did not look at the store's page — the v0.29.2 rule), **no `check_attempts` row** (that table measures what the STORES answered; a keystroke is not a request and would corrupt the one dataset built to judge them), and **no `store_unit_price_sek`** (no printed jämförpris exists, so the validator skips the row instead of comparing our arithmetic with itself). An ordinarie makes it an offer in the v0.25.2 shape with `offer_type="manuellt pris"`, so the deal row, the email and the history table all show that a human typed it; without one it is simply a price that was charged. The date is a Swedish civil day converted at **midday**, not midnight — a note dated today must land AFTER that morning's scheduled check to become the link's latest point, which is what puts it in this week's buy list; backdating it makes it history and floor only. `offer >= price` is refused here too (v0.32.1), because this is the one place a human can type the inversion directly.
- **A deal is judged on TWO axes since v0.48.0, and both live in `domain/deals.py`.** The verdict is space (cheapest of the product's links right now); **`timing` is time** — this price against `lowest_unit_price_sek`, the product's cheapest kr/enhet OBSERVED across all its links inside `PRICE_LOW_WINDOW_DAYS` (84). `poor` = at least `SEEN_CHEAPER_MIN_PCT` (10 %) above that floor, `good` = under it, `unknown` = no comparable history. Born in prod 2026-08-04: Bryggkaffe Mellanrost 450 g at ICA Björksätra, "2 för 130 kr" = 144,44 kr/kg, cheapest of three links and therefore BEST — while the same coffee had been 110,00 kr/kg at Willys nine days earlier. It led the buy list; five of the six rows beside it sat at **0,0 %** above their own floor, which is what a genuine campaign looks like (it sets the new low). **Ten percent, and not the span bar's position:** the bar's position moves with an outlier HIGH, which is not evidence about this price, and a tighter threshold would demote real campaigns on quantity-rounding noise alone. **The floor query counts INACTIVE links** — the deliberate opposite of the best-alt rule — because "have I seen this cheaper" is about a price that was really charged, not about a shelf we can reach today. A `poor` row is **demoted, never hidden**: Att köpa puts it in its own collapsed section above the WORSE one, with the percentage, the floor price, the butik and the date in the row; the Monday email drops it exactly as it drops WORSE (the email IS the buy list, and the two must not disagree — Gotcha 4); MCP carries the fields. Consequently the page heading counts what SURVIVES both filters and says "värda att köpa nu", not "billigast just nu" — the old wording would undercount things that genuinely are billigast just nu, and claimed nothing about whether buying them was a good idea.
- **Att köpa (Erbjudanden until v0.47.0) is grouped by whether the offer is actually the cheapest way to buy the product, not by when we checked.** The three-way split — **BEST** (`unit_price_sek <= best_alt_unit_price_sek`), **WORSE**, and **UNKNOWN** (either is null — no amount on the link, or the product has no other link) — **is computed in `domain/deals.py` since v0.41.0** and rides the wire as `verdict` + `savings_per_unit_sek`; the portal's `classifyDeal`/`dealSavings` are READERS of those fields, never a second derivation (the weekly email needs the identical judgement, which is exactly the Gotcha-4 setup). BEST + UNKNOWN render under "Värt att köpa" ranked by the **kr/unit margin over the next-best link**; WORSE goes in a collapsed `<details>`, least-bad first. The discount % is the STORE's framing and ranks nothing — 30 % off a bad price is still a bad price, and ordering on `checked_at` put exactly those rows on top. UNKNOWN rides with the buyable ones deliberately: it is not *known* to be bad. The "Köpvärda erbjudanden" stat counts BEST only (tooltip carries the full breakdown). **`GET /deals` still orders by recency and still returns every offer** — the ranking is a view, and `find_deals`/MCP consumers keep their contracts (they too now carry the verdict). All three former copies of the deal query (admin route, service, scheduler summary) collapsed into `deals.current_deals`; the admin copy's recency-dedupe had already drifted — it kept showing a link's superseded offer after the latest point had none, which the latest-per-link JOIN makes impossible. **Both queries filter on `is_active` (v0.41.2)** — the deal AND its alternatives: an inactive link's frozen last price is not a shelf anyone can buy from, and letting it win as `best_alt` flipped a genuine BEST to WORSE, which the weekly email then dropped (pinned by a real-Postgres test in `test_deals.py`). **The deal row's product name is a button into the price-history modal (v0.42.0)** — the same `showPriceHistory` modal as Produkter (the /deals wire already carries `product_id`/`product_name`/`unit`; name + unit resolve from the client-side `allDeals` cache, NOT `allProducts`, which may never have loaded). Only the NAME is the target — no whole-row fallback, because the butik cell is already the link OUT to the store; a hover-triggered graph was rejected outright (no hover on the phone in the aisle, and a Chart.js render + API call per swept row).
- **The product ROW is the Länkar button, and each removed action went where its context already lives.** Five buttons per row (Länkar / Länka / Historik / Redigera / Ta bort) meant 75 controls on a 15-product screen, two of which differed by one letter while doing different things. Now: the row opens the links panel, which is what the table leads into — **the visible affordance is the product NAME, a real `<button>`** (focusable, Enter works), with the rest of the row as a quiet convenience target; **the Åtgärder cell is excluded from that target** (`td.row-actions`), because empty space beside two buttons that silently opens a panel is an invisible third button, reported as a graphical bug within a day of shipping v0.34.0. **Länka butik lives IN that panel** (the dialog stacks above it via `#modal-link-store { z-index: 210 }` and refreshes it on save); **Ta bort lives in the edit dialog** beside the fields it destroys, and its confirm names the product and counts the links + history going with it. The card header keeps ONE primary button (Snabbtillägg, the 95 % path); Ny produkt / Exportera / Importera sit in a `<details class="menu">` overflow. **The links panel follows the same shape (v0.34.2):** its row keeps Redigera + Kontrollera nu, and deleting a link lives in the "Redigera länk" dialog as **Ta bort länk** — "Avlänka" was jargon rather than Swedish, and a third button on every link row for something done twice a year. Its confirm names the butik and the package, because "butikslänken" is ambiguous with three of them on screen. **Do not put such a menu inside the products table:** `#products-table-container` is an `overflow-x: auto` box, which computes `overflow-y` to `auto` and clips the last row's dropdown. **The row's badge (erbjudande / saknar mängd / en butik) sits beside the NAME (v0.53.1)** — it is a property of the product, and on the right it was right-aligned against the price column, which read as a statement about the butik standing next to it and moved horizontally from row to row with the price's width.
- **The product list filters in the browser; `allProducts` is ALWAYS the full list.** `loadProducts` fetches `/products` unfiltered and `renderProducts` filters between the array and the DOM. Before, the search round-tripped per keystroke *and assigned the result to `allProducts`*, so the global list silently meant "whatever the table is filtered to" — which is what the watch dialog's product `<select>` reads. Facets (kategori, butik, täckning as `<select>`s; omfång, status = har erbjudande / saknar pris / **trasig länk, v0.40.0** and sort order as CHIPS since v0.47.0 — **"saknar mängd" left this row in v0.53.1**: the field that closes that gap is on Fel & luckor, one row per link, saved in place, so a chip here only narrowed a list you then had to leave anyway. A stored `needs_amount` status is cleared on restore rather than filtering with no chip on screen to switch it off) are built **from the data** with their counts, so a filter can never be offered that returns nothing. The chips are delegated and the four selects bind by id at top level — `test_static_gates.py` gates those four ids (it asserts the COUNT too, so moving a facet between the two forms is a deliberate edit, not a silent one). **Trasig länk is DERIVED per read, never persisted:** `domain/link_health.py` is THE judgement (the link's last 3 non-blocked `check_attempts` all failed — one "ok" clears it by construction, same self-clearing shape as `quantity_mismatch`), every link row carries `is_broken`/`broken_detail` (both `_link_payload` in admin.py and `get_links_for_product` in service.py — the Gotcha-4 twins — resolve through the one `broken_links` query), the facet option appears only with a hit count ("Trasig länk (2)") and the links panel shows a badge whose tooltip carries the last HTTP status. **BLOCKED attempts are invisible to the judgement in both directions** — a wall neither counts as a failure nor interrupts a streak, because an ICA challenge evening must not paint 44 valid links as broken and invite their deletion (the v0.19.0 misread). Deliberately no auto-retirement and no URL-repoint action: the URL is the link's identity, so a moved page is a new quick-add link plus Ta bort länk on the old one. **The täckning facet asks the inverse question — "vad jämför jag INTE?" (v0.38.0).** The whole point of the tracker is comparing the same product across chains, so the interesting rows are the products that exist at one chain and not the other. It keys on **`store_slug`, not `store_name`** — two ICA butiker are two links under ONE chain, and `store_name` carries the butik label ("ICA Maxi Sandviken"), so a name-keyed gap would ask the wrong question. It **requires at least one link** (a product with none is not a comparison gap but a half-finished product; "Saknar pris" is that filter), and it composes with the existing butik facet: "Butik: Willys" + "Saknar ICA" is the query stated exactly. **`STORE_OWN_BRANDS` (in `admin.html`, keyed by store slug) is what keeps it usable, and it is MEANT to be extended** — an ICA-branded product will never be at Willys, so without the exception it is a gap that can never be closed and sits at the top of the list forever. On live data it hid 5 of 11 rows in "Saknar Willys", all of them ICA-branded. Own brands are excluded only from FOREIGN chains: an ICA-branded product with no ICA link is a real gap and stays. Matching is exact and case-insensitive, so "ICA Basic" needs its own entry — it inherits nothing from "ICA". Each option carries the count it would show ("Saknar ICA (4)"), smallest gap first, which is why no threshold is needed: "Saknar Lyko (22)" is self-evidently not a comparison gap. Chains with no gap are not offered at all — same rule as the other facets. The "Sortera: butiksordning" chip uses `domain/categories.py`'s walk order, read back off the server-injected `#edit-product-category` options — **a view of THE list, never a second copy** (uncategorised sorts last). State lives in `sessionStorage`, **not in the hash**: `currentPage()` parses the whole fragment as a page name. `/products?search=` stays for the REST API and MCP. The wiring binds by element id at top level, so a renamed control throws mid-load and leaves the whole page inert — `test_static_gates.py` gates those ids against the markup.

**A dialog announces itself, and `openModal` is THE way one is opened (v0.56.1).** The portal is read by a READER role — the household the Entra gate lets in — and v0.29.0 exists because one of them actually logged in, so this is real usage rather than a hypothetical audience. Four rules, each of which fails invisibly (nothing on screen looks different when they rot, which is why all four carry gates in `test_static_gates.py`):

- **`aria-modal="true"` is a promise markup cannot keep alone.** It asks assistive tech to ignore everything OUTSIDE the dialog, so focus must BE inside it — otherwise the reader is parked on a button their own reader can no longer describe. The attribute and the focus handling ship together or neither should: **`openModal(id)` is the single entry** (ten call sites used to set `display` by hand), a Tab handler keeps focus in the topmost dialog, and `closeModal`/`syncHistoryToHash` hand it back to the opener. **Focus goes to the first FIELD, not the first focusable** — the × sits in the header and wins a plain DOM-order query, which lands the reader on "close" and makes Enter dismiss what they just opened (found by rendering the page, not by reading it). Stacked dialogs keep the OUTERMOST opener: "Länka butik" over the links panel must not send focus back into a panel that is itself closing.
- **A label that merely sits beside its input names nothing.** Both valid shapes are accepted — `for=` resolving to a real id, or the control nested inside the label (how the checkbox rows are written). `aria-labelledby` is checked against real ids because a typo'd reference is WORSE than none: the dialog is unnamed either way, but the attribute claims otherwise.
- **The toast's timer is load-bearing.** It is the only feedback several actions get. `clearTimeout` before re-arming, or the next toast inherits the previous deadline — the import summary ("Import klar: N skapade, M bevakningar"), one of the few toasts carrying counts recoverable nowhere else, was the likeliest casualty because dwell was a fixed 3 s regardless of length. Dwell now scales with reading time, an error outlives a success, and the text is blanked before it is set (`role="status"` announces a CHANGE, so the same message twice was silent).
- **Rendering is how this class of bug is found.** `node --check` says the file parses; it cannot say the × was focused. The recipe — assemble shell + fragments, stub `window.fetch`, drive it in the Chromium in `~/.cache/ms-playwright/` — caught two defects in this very change. Note the trap it also caught: a control on a hidden `.app-page` cannot be focused, so a probe that opens a dialog from another page tests nothing.

**Design handoffs live outside the repo, and what a review REJECTED is the part worth writing down.** `design_handoff_*/` is gitignored (v0.53.0; "3a" in v0.47.0 was likewise never committed) — an interactive prototype is a reference for one round, not source, and its mock arrays invite being read back as facts about the app. The 2026-08-11 review ("förenkling") was adopted in the two places above. **These parts were refused, and the reasons outlive the handoff:**

- **A "silent error" row showing the shown price struck through and the true one beside it, with a "Byt källa" picker.** The app does not know which figure is right, and says so on purpose: a tier regression is cause-neutral (the store changed shape, OR the link has not been re-checked since an extractor improved) and a jämförpris mismatch means "either the price or the amount is wrong". Presenting one number as truth is a claim `domain/validation.py` refuses to make, and a per-link extraction-source override contradicts the ladder itself — the tier is code, `EXPECTED_SOURCE` is derived from the registries.
- **Collapsing Produkter's facets** to search + trend chips: it drops the butik filter, the four status facets (incl. **Trasig länk**, v0.40.0), the `categories.py` walk-order sort, and the 10-value category enum (the proposal's "Livsmedel/Apotek" is `store_type`, which is the scope switch, not a category).
- **Losing Snabbtillägg / Exportera / Importera from the Produkter header**, and moving the links panel behind a row overflow menu — the row IS the links button, and Exportera is THE backup.
- **Modelling a watch with ONE target** (→ watches-page bullet), **shortening `offer_details` to a badge** ("Max 2" for "Välj & blanda! 2 för 99,00" — the price only exists under the condition, v0.41.2), **making the deal row's butik plain text** (it is the link OUT), and dropping the `in_stock` marking (v0.50.0: mark, never hide).
- **Everything in it is desktop-only** (fixed 160 px + 160 px + price columns at a 1440 preview). Att köpa is read in the aisle; the phone layout is not a later concern for that page.

**Bevakningar groups on what the reader can DO, and one group exists because it was invisible (v0.53.0).** A watch row has always answered "how close is it?" with a bar. What it could not answer is whether the question has an answer at all: a target below every price the product has ever been observed at is not a strict watch, it is a watch that **cannot fire**, and it rendered exactly like one that is merely waiting — forever, silently, which is the same failure class as the ICA campaigns `domain/validation.py` exists for. Four groups, in this order: **under målet nu** (buy if you need it) · **inom räckhåll**, closest first by the gap as a PERCENT of the target (the groups mix units — 0,29 kr/l and 4,00 kr/kg say nothing about which is nearer) · **larmar inte som det är satt** · **utan mål** (alarms on any offer — a setting, not an omission). An empty group prints nothing; an empty "larmar inte" heading would read as a warning where there is none. The count of unfireable watches also rides the page's own summary line, for the same reason.

- **The evidence is `domain/deals.observed_spans`, made PUBLIC rather than copied** (it was `_floors`). Same window (`PRICE_LOW_WINDOW_DAYS`), same ≥2-observations rule, same "inactive links count". A second hand-written floor query would drift from the buy list's within a release (Gotcha 4) and the two disagreeing about what a product has cost would be invisible until an alarm quietly never went off. `/watches` carries `lowest_unit_price_sek` / `highest_unit_price_sek` / `lowest_seen_at` / `lowest_store` / `span_window_days`.
- **Only a kr/enhet target may be judged against the span, and that is a hard rule.** An absolute `target_price_sek` is a PACKAGE price; a 100-pack and a 20-pack of one product share a kr/tabl. and have wildly different kr, so placing one on the other's axis is the g/kg class of error (it pinned a cheap link to the expensive end of the bar in the first render of this feature). An absolute target is never called unreachable and never gets a marker — it keeps the distance bar it always had, which says less and is true. **Both targets stay named in every row's meta line** either way: the scheduler alerts on whichever is set, and a target the page does not show is an invisible trigger (v0.27.0).
- **The target is a SECOND mark on the bar, deliberately not the same one as the current price** (`.span-target` vs `.span-marker`) — a reader who confuses them reads the row backwards. A target outside the span gets an edge arrow rather than a tick clamped to 0 %: clamping would draw it AT the floor and quietly deny the very problem the row is reporting.

**The weekly email is a buy list, and its recipient is configuration (v0.41.0).** `_check_weekly_summary` sends once per Monday from the END of the förmiddag window — 12:00 **Swedish wall-clock** via `schedule.weekly_summary_slot`, the first moment the week's Monday checks (ICA and Willys both) are in; the in-memory dedup keys on the LOCAL Monday date, **and only a send that returned True stamps it (v0.41.2)** — `ResendEmailService.send` never raises, so failure is a RETURN VALUE, and the old code discarded it: a Resend outage at noon lost the week's buy list while `summaries_sent` and the log claimed success. A False (or an exception) leaves the date unstamped, so the 5-minute loop retries for the rest of the local Monday. (The old rule was "Monday 14:00" applied on naive UTC — 15/16 Swedish depending on DST, the same silent drift v0.33.0 removed from the check window.) Content is the portal's "Värt att köpa" as an email: **BEST + UNKNOWN from `domain/deals.py`, WORSE filtered out in the scheduler** — an offer another link beats per unit is information, not news — grouped per butik by the notifier (one section per butik = one leg of the shopping round), and any row older than `DEAL_STALE_HOURS` dated ("sett fredag 24/7 — kan ha hunnit ta slut"), never hidden. **Since v0.53.2 the third column is the SPAN BAR, not the margin against another butik** — "0,45 kr/kg billigare än ICA Maxi 1 kg" answered the wrong question for a buy list: cheaper than the next link says nothing about whether *either* price is any good, and both can sit at the top of a span the product has spent twelve weeks below while the row still reads as a win. The margin survives as the SORT KEY inside each butik's section. The bar is **tables and percentage widths, never absolute positioning** (Outlook renders through Word, which has no `position`, and a collapsed bar would take the row's only judgement with it) and the fill's right edge IS the marker — an email cannot afford a second element overlapping the first to say the same thing. It makes the portal's three refusals in the portal's words (no jfr-pris / one observation / the price has not moved), and a row whose link has no mängd says that ONCE: the span cell already names the fix, so the UNKNOWN verdict line stays quiet. `_span_html` in `notifier.py` and `dealSpanHtml` in `admin.html` are twin RENDERINGS of one dataset (the deal row's own lowest/highest — there is no second query); email HTML cannot share the portal's stylesheet, so keep their wording and thresholds in step by hand. No top-N cap — the old top-10-by-recency silently dropped real wins. **The recipient is `SUMMARY_EMAIL`, falling back to `ALLOWED_ENTRA_EMAIL`** (the Entra UPN — set `SUMMARY_EMAIL` when that is not a deliverable address), and is NEVER derived from watch rows: the old sender mailed the union of watch emails, so a tracker with products but no alarm sent nothing — the digest existed only as a side effect of the watch feature. The watched-products section (lowest current kr/enhet per bevakad produkt) still rides along. Per-product watch alerts are unchanged and remain the "tell me NOW" channel.

**MCP surface: four tools, and the module docstrings in `src/mcp_server/server.py` are THE description.** `check_price` (last OBSERVED price per listing — reads history, never fetches), `compare_stores` (every tracked package of one product, ranked on the COMPUTED kr/enhet, amount-less listings last and saying so), `find_deals` (every current offer, no cap, each row carrying `verdict` AND `timing` plus villkor and lager — → deals bullet), `list_products`. **Do not read the surface off EXTRACTION.md §5**: that table is the May-2026 spec and is superseded on both halves a caller cares about — the mount was still an open question there ("`/mcp` path OR a separate Traefik subdomain. Decide during Phase 4" — decided by D-29) and its "List of current offers" predates every judgement `find_deals` now renders. A tool's output is user-facing text, so it is Swedish and it follows the portal's wording: change one and check the other two surfaces (portal, weekly email) for the Gotcha-4 drift.

**Quick-add (v0.5.0):** `POST /quick-add/preview` + `POST /quick-add` create a product AND its store link from one pasted URL (store matched by hostname, package parsed from the title). **The preview's identity ladder mirrors the price-check ladder: store API → store page-state → JSON-LD → LLM (v0.25.1; page-state tier v0.31.0).** For a store with a structured API — `domain.parser.get_api_extractor`, currently only Willys — it reads identity + package straight off the REST API (`WillysApiExtractor.extract_metadata`) and never fetches the page. That tier exists because **Willys is a client-rendered SPA: its product HTML carries no JSON-LD and no price**, so the HTML→LLM ladder saw an empty shell and returned a blank form. A store in `get_html_extractor` (Rusta and Lyko; Clas Ohlson and ICA are registered there but return None for metadata — their JSON-LD already carries what the preview needs) gets its identity from the fetched page's hydration state instead (`extract_metadata_from_html`) — Rusta's JSON-LD names are bare ("Deo roll-on Nivea") while CURRENT_PAGE's `subTitle` carries the package text the preview form wants prefilled, and Lyko's `entryName` is already the abstract good with brand AND size stripped ("Hand Wash Refill Milk & Honey" out of "Palmolive Hand Wash Refill Milk & Honey 500 ml") with `size`/`unit` giving the package as numbers. The pharmacies still take the JSON-LD path — verified 2026-07-26 that all five serve a parseable Product node server-side. The suggested name is the abstract good — `strip_brand_from_name` drops a leading/trailing brand the source folded in (v0.22.0), so it doesn't double-print beside the brand column. Preview-then-confirm on purpose — the confirm step is where "ny produkt" vs "ny länk på befintlig produkt" gets decided, which keeps quick-add from rebuilding the pre-04.1 one-product-per-pack-size shape. Decision logic is pure functions in `domain/quickadd.py`; full design in `docs/quick-add.md`.

**Auth:** The portal + API are served at the app root (`price.<domain>/`); the `/admin` prefix was dropped (old `/admin` URLs 308-redirect to `/`) — D-28. The UI trusts the `X-Auth-Request-Email` header forwarded by the upstream ingress and validates it against `ALLOWED_ENTRA_EMAIL` (which must match the Entra **UPN**, not necessarily the gmail address).

**Header trust has an optional second factor since v0.51.0:** when `INGRESS_SHARED_SECRET` is set, every request must also carry it in `X-Ingress-Auth` (compared constant-time BEFORE the email header is read) — closing the hole where anything that can reach the container port directly (a neighbour on the docker network; the reachability mcp_server/auth.py documents) could claim to be the admin. Unset = old behavior; enabling is a two-sided move (env here, `customRequestHeaders` on the Traefik router in home-server).

**Two roles since v0.29.0 — admin writes, everyone else reads.** `ALLOWED_ENTRA_EMAIL` is now the **admin**, not the only allowed user: anyone the upstream Entra gate authenticates is a **reader**. THE gate is `auth.require_admin_for_writes`, mounted **once** as the `APIRouter(dependencies=[...])` in `admin.py` — it authenticates every caller and refuses any method outside `SAFE_METHODS` (`GET`/`HEAD`/`OPTIONS`) from a non-admin. **Deny-by-default and keyed on the HTTP method, not on a per-route marker**, because a decorator you have to remember on 14 write endpoints is a hole waiting for the 15th; `test_static_gates.py` (AUTHZ-01/02) fails the build if the dependency is dropped or a route is registered off a second router. Every read is a GET here, so no exception list exists — and that is by decision: `/export` (a full DB dump) and `/logs` are readable by every reader. `get_principal` is the ONE identity point (`require_auth` resolves through it); a test that overrides only `require_auth` leaves the write gate live and 403s every POST. The UI mirrors the role rather than defining it: `render_admin` stamps `<body class="role-admin|role-reader">`, CSS hides `.admin-only`, and the JS builds row actions off `IS_ADMIN` — the server is still the gate, this only stops offering buttons that can only fail. Before the split, a household member who logged in correctly got a **403 from this app**, which the ingress then dressed as a white page reading "Found" (→ Gotcha 7). Entra ID enforcement itself is **live in production since 2026-07-09**: oauth2-proxy v7.15.2 + Traefik `forwardAuth` (`entra-auth@file`), email claim = `preferred_username`/UPN, managed in the home-server repo — not in this app. The MCP server is served at `price.<domain>/mcp/` (no `mcp.` subdomain — a path-scoped, un-gated Traefik router with explicit priority bypasses the Entra gate for `/mcp` only) and is protected by its own static bearer token; without `MCP_BEARER_TOKEN` the endpoint fails closed (503). See EXTRACTION.md §6 for background, though its original in-app-OIDC description was superseded by this IAP header-trust model, and D-18's `mcp.<domain>` subdomain plan was superseded by the `/mcp` path (D-29 in .planning/STATE.md).

## Releasing — shipping is part of the task, not a separate errand

**A fix that is not released is not delivered.** Prod runs a *pinned image tag*, so work that only reaches `main` changes nothing for the person using the app. Unreleased commits used to pile up for days (12 of them by v0.3.2 — a whole ruff/CI rebuild plus the price-history fix, all sitting on `main` doing nothing).

**Standing rule: when a change is user-visible or fixes a real problem, cut a release as the last step of the task — without being asked.** Do it in the same session as the fix.

Release = push a `v*` tag. That is the only trigger; `.github/workflows/release.yml` then builds and pushes `ghcr.io/magter/price-tracker:vX.Y.Z` (+ `:sha-<commit>`) for amd64. Nothing else in this repo deploys anything.

```bash
# 1. main is green and pushed. Never tag a dirty tree or an un-pushed commit —
#    the tag would point at something no one else can fetch.
poetry run ruff check src tests && poetry run ruff format --check src tests && poetry run pytest -q
git push origin main

# 2. The version in pyproject.toml IS the tag. Bump it, commit it, then tag that commit —
#    a tag whose code says a different version is a lie you will read back later.
#    (It said 0.1.0 while prod ran v0.3.2. Don't let that happen again.)
git tag vX.Y.Z && git push origin vX.Y.Z

# 3. Watch the build. A tag that fails to build is not a release.
gh run watch "$(gh run list --workflow=release.yml --limit=1 --json databaseId -q '.[0].databaseId')"
```

**Version choice** (single-user app, so this is deliberately simple):
- **patch** (`v0.3.2` → `v0.3.3`) — a bug fix, a corrected display, an internal cleanup.
- **minor** (`v0.3.x` → `v0.4.0`) — a new capability, a schema change, or anything that alters how the app is operated or deployed.
- A schema change means **a new alembic revision** (additive, on top of the chain — see Gotcha 3 for why a shipped revision is never rewritten in place). The deploy applies it via `alembic upgrade head`; verify with `alembic check`, not `alembic current`.

**Then tell Magnus the tag is built and needs the deploy bump** — and say which version is pending against what is pinned *right now*, read with the command in the Deploy state paragraph, never recalled. Deploying is a one-line change to the pinned tag in the home-server repo's `compose/dokploy-apps/price-tracker/docker-compose.yml`, which **Magnus makes himself in the GitHub web UI** (GitOps split: this repo builds, the platform repo is the deployment truth). **That repo is not this repo — do not edit it from here**, and the release is not live until that bump lands.

Docs-only, planning-only, or test-only commits do **not** earn a tag; they ride along with the next real one.

## Gotchas

Traps that already cost time. Each one **passes silently** — that's why they're here.

1. **`ruff` exists — and `B008`/`S101` are ignored on purpose.** ruff 0.14.4 is a declared dev-dependency, with the config inherited from the source repo (`ai-agent-platform/services/agent`); Phase 1 rewrote `pyproject.toml` from scratch and dropped it, which is why the planning docs kept assuming a ruff that wasn't there. Run `poetry run ruff check src tests` and `poetry run ruff format src tests` (`ruff format` is black-compatible and **replaces** black — do not add black). **Never "fix" `B008`:** it is FastAPI's `Depends()`-in-default-argument pattern, and hoisting the call out of the default argument breaks dependency injection — and with it the auth guard. `S101` is ignored because `assert` is how tests assert. **The test suite is the truth, not the linter:** if an auto-fix turns a test red, the fix was wrong — revert it (`UP017` and `UP032` rewrite real logic, not just style).

2. **`src/api/templates/admin.html` has no `<script>` tag.** It is three fragments split on `<!-- SECTION_SEPARATOR -->` and reassembled at request time by `price_tracker_dashboard` in `admin.py`, together with `templates/shell.html` + `templates/shell.css` (the outer document, sidebar, header, mobile chrome and the design-system CSS — Python string literals until v0.51.0). A gate that extracts the `<script>` body gets **zero bytes**, and `node --check` on empty input **exits 0** — so it passes no matter what you wrote. The working incantation:
   ```bash
   awk '/SECTION_SEPARATOR/{n++;next} n==2' src/api/templates/admin.html > /tmp/admin.js \
     && test -s /tmp/admin.js && node --check /tmp/admin.js
   ```
   Keep the `test -s` guard. And remember: **"the file parses" is not "the page renders."** Verify rendering separately.

3. **Alembic: `0001_initial.py` was rewritten in place** during Phase 04.1. Alembic does not checksum migration bodies, so a database stamped `0001_initial` from BEFORE that rewrite compares equal to head, runs **nothing**, and exits **0** — the app then boots quietly against the **old** schema. **`alembic current` will not reveal this** — it prints the same revision either way. **Only `alembic check` does.** That trap was resolved by the 04.1 volume drop (`README.md` § "Schema reset (Phase 04.1)"). **Since v0.6.0 the chain is normal again:** `0002_store_label` is a real additive revision on top of `0001_initial`, and schema changes from here on are ordinary new revisions applied by `alembic upgrade head` — never rewrite a shipped revision in place again.

4. **RESOLVED (v0.51.0) — the two `get_price_history` are one.** THE query and row shape live in `domain.service.price_history_rows`; the service method wraps it with the MCP error contract (failure → empty list) and the `/products/{id}/prices` route with the HTTP one (400/500). Before the collapse the copies had drifted twice (package data missing on the wire; a truthiness test rendering a legitimate 0.00 as null). The general lesson stands: a second hand-written copy of a domain query WILL drift — `latest_point_per_link` in `domain/models.py` closed the same pattern for the "latest point per link" subquery (five copies, two semantics).

5. **A handler on the app loggers is what silences `docker logs` — `logbuffer.install()` must keep calling `ensure_console_logging()` first (v0.28.1).** Nothing configures the ROOT logger (uvicorn only configures its own `uvicorn*` loggers), so root has no handlers and Python falls back to `logging.lastResort`, which prints WARNING+ to stderr. But `Logger.callHandlers` uses `lastResort` **only when it finds zero handlers anywhere up the chain** — so the instant v0.18.0's ring buffer attached to `domain`/`infra`/`api`, a handler WAS found, the fallback was skipped, and every app record terminated in memory. **Nothing raised and the portal's Loggar page kept working**, which is exactly why it went unnoticed: seven days of prod logs contained no app line at all, only uvicorn access logs. `alembic current`-style checks won't show it either — the only test is to look for a non-uvicorn line in `docker logs`. Note the ordering trap: adding a handler to any app logger *before* root has one re-creates this. Covered by `TestConsoleLoggingSurvivesTheRingBuffer` in `tests/test_logbuffer.py`.

6. **`alembic/env.py` must keep `disable_existing_loggers=False`.** `fileConfig()` defaults that flag to **True**, which sets `disabled = True` on every logger that already exists — including the app's own `domain`/`infra`/`api`. Nothing raises: the loggers simply stop emitting, so app logs and the portal's Loggar buffer go quiet. Invisible when alembic owns the process (the deploy runs it standalone), fatal in any process that ran the app first. It surfaced as two `test_logbuffer` failures the moment a DB-backed test file happened to sort before it — and the tests passed in isolation, which is what makes it a gotcha rather than a bug report.

7. **The ingress replaces the BODY of every 401–403 this app returns, and a 403 keeps its status.** The `entra-auth-errors` Traefik middleware (home-server, `bootstrap-dokploy.sh`) catches `401-403` from the *whole chain* — the forwardAuth's own 401 **and** any 403 the app itself produced — and serves the body of `oauth2-proxy`'s `/oauth2/sign_in?rd=…` instead. Its `statusRewrites` maps **only 401→302**, so a 403 comes back as **403 with a redirect's body**: `<a href="…">Found</a>.` The browser does not follow a 403, so it renders a white page with the word **"Found"** on it — which is what a non-admin user saw before v0.29.0, and reads like a broken app rather than "access denied". Consequences that outlive that fix: **never put user-facing meaning in a 403 detail** — a JSON API 403 reaches the frontend as that HTML, which is why `apiPost/apiPut/apiDelete` in `admin.html` substitute their own Swedish message on 403 instead of echoing the response body. Narrowing the middleware to 401 only would fix it at the source, but that is the **home-server** repo, not this one.

8. **An endpoint with no test rots silently.** `/export` + `/import` had **zero** tests and drifted until the export backed up nothing while still returning 200 OK. Both are now covered by a real-Postgres round trip (`tests/test_export_import.py`). Before trusting any endpoint that no test names, check what it actually returns against real data — a green suite says nothing about code it never calls.
