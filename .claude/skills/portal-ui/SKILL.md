# Portal UI

The served page and its six hash-routed pages. The judgements it displays (verdict, timing, statistics, validation) are defined in the `price-judgements` skill; the portal only reads them off the wire.

Moved verbatim from `CLAUDE.md` at `88e99e9` by the information-layout move (`git log -- .claude/skills/portal-ui/SKILL.md` names the commit). A pointer of the form "→ X bullet" names a bullet by its subject; it may sit in another project skill — `AGENTS.md` lists all four.

## The template, and how to check it

2. **`src/api/templates/admin.html` has no `<script>` tag.** It is three fragments split on `<!-- SECTION_SEPARATOR -->` and reassembled at request time by `price_tracker_dashboard` in `admin.py`, together with `templates/shell.html` + `templates/shell.css` (the outer document, sidebar, header, mobile chrome and the design-system CSS — Python string literals until v0.51.0). A gate that extracts the `<script>` body gets **zero bytes**, and `node --check` on empty input **exits 0** — so it passes no matter what you wrote. The working incantation:
   ```bash
   awk '/SECTION_SEPARATOR/{n++;next} n==2' src/api/templates/admin.html > /tmp/admin.js \
     && test -s /tmp/admin.js && node --check /tmp/admin.js
   ```
   Keep the `test -s` guard. And remember: **"the file parses" is not "the page renders."** Verify rendering separately.

*From the release index, removed by the information-layout move:*
- **The page is served `Cache-Control: no-cache` (v0.45.1).** Without it a browser kept a heuristically cached copy of the whole UI across deploys — right after v0.45.0 a cached page enforced the old `step="0.01"` and read as "the fix didn't work". no-cache (revalidate, not no-store) suffices because the response carries no validator.
- **A package-amount `step` is set in TWO places (v0.53.3).** The three inputs carry `step="any"`, and `pkgFieldsChanged` once re-assigned `amountEl.step = '0.01'` on every dialog open, so 0,024 kg failed with `stepMismatch` while 24 g passed. A static gate covers both the markup attribute and the JS assignment. `st` keeps `step='1'`: a count is whole.
- `tests/test_static_gates.py` gates EVERY `getElementById` literal (v0.41.3); the `/stats` and `/scheduler/status` wire shapes are pinned (v0.51.0).
- Chart.js is `defer`, and `loadDeals`/`loadStatistics` carry request-sequence tokens so the last RESPONSE no longer wins (v0.51.0). `loadStores` is guarded (one 500 used to blank the whole app), `loadExport` no longer saves a 500 body as the backup, and the span bar no longer claims "en observation" when `/stats` fails (v0.49.1).
- `#stats-container` is under the never-scroll-sideways rule, and a watched product without a price renders without "None kr" (v0.41.3).

## Rendering the portal without a server

Gotcha 2 (above) says "the file parses" is not "the page renders". This is how to render
it on the dev machine, with no server, no DB and no network. (Moved from agent memory
`render-check-admin-html`, written 2026-07-30 to 2026-08-13, in the information-layout
move; the Chromium build directory below is the one that existed on 2026-08-13 — read
the current one with `ls ~/.cache/ms-playwright/`.)

1. `python -c` → `api.admin.price_tracker_dashboard(Principal(email=..., is_admin=True))`
   returns the whole page as a string (it only reads the template; nothing async touches the DB).
2. Inject a `<script>` into `<head>` that replaces `window.fetch` with a table of canned JSON
   per path (`/products`, `/deals`, `/watches`, `/stores`, `/scheduler/status`,
   `/products/<id>/links`), and drop the `/static/chart.umd.min.js` tag — it 404s on `file://`
   and only the history modal needs `Chart`.
3. Render or drive it with the Chromium that playwright already downloaded:
   `~/.cache/ms-playwright/chromium-1228/chrome-linux64/chrome --headless=new --no-sandbox
   --virtual-time-budget=15000 --screenshot=out.png "file:///…/preview.html#/produkter"`.
   `--virtual-time-budget` runs the page's timers, so `setTimeout`-staged clicks execute.
4. For interaction tests: append a script that clicks things on successive ticks and writes
   results into a `<pre id="testlog">`, then read it with `--dump-dom` (headless Chrome cannot
   answer `confirm()`, so delete flows stop at the dialog).
5. `--window-size` below 500 wide is a TRAP: headless Chrome clamps the viewport to 500
   (`window.innerWidth` says so) but crops the screenshot to the requested width, so the page
   looks clipped at its right edge — it reads exactly like a layout-overflow bug and is not one
   (cost a false lead 2026-07-30). Phone-layout checks: use 500×1000 (still under the 768px
   breakpoint) and trust it.

**Stub-shape trap** (cost a false lead 2026-08-04): the canned `/stats` JSON must carry the REAL
top-level keys — `period` (with `days_of_history`, `observations`, `first_observation`),
`products`, `stores`, `coverage` (with `products_priced`), `data_quality` — or
renderStatistics throws inside loadStatistics's try, the catch paints "Kunde inte ladda
statistik", and every downstream render in that try (renderDeals' span bars, renderLuckor)
silently never runs: reads exactly like a product bug in whatever you were checking. Crib
the shape from `stats.py`'s return dict, not from memory. And grep the RENDERED state via
an injected testlog `<pre>`, never `grep` on --dump-dom output alone — the JS source text
in the dump contains the very error strings you are grepping for.

**Stub-routing trap** (cost a false lead 2026-08-12): if the stub picks its canned entry with
`Object.keys(d).find(x => p === x || p.indexOf(x) === 0)`, the short key wins — `/products`
shadows `/products/<id>/prices` and `/products/<id>/offers`, so the modal renders eight empty
rows (the product list, read as price points) and looks like a data bug. Sort the keys
longest-first before matching. Also note `json.dumps` writes `"/logs": []` WITH a space, so
string-patching an existing stub on `"/logs":[]` silently matches nothing — rebuild the dict
and re-serialize instead.

To render the price-history modal the Chart.js tag must be KEPT, not dropped — point it at
`file:///…/src/api/static/chart.umd.min.js` and pass `--allow-file-access-from-files`.

Also usable as a node harness for the pure JS: run the third `SECTION_SEPARATOR` fragment in a
`vm` context with a stub `document`, rewriting top-level `let`/`const` to `var` — in a vm
context lexical declarations are NOT properties of the context object, so tests otherwise
cannot read or set `allProducts` / `productFilters`.

## Client-side ranking and filtering

**The portal ranks and filters CLIENT-side, and the endpoints keep their contracts (v0.34.0, rebuilt as "3a" in v0.47.0).** UI decisions that are easy to undo by accident:

- **Att köpa's margin is a PERCENTAGE, it is the ORDER, and since v0.53.1 it is not printed on a best row.** `savings_per_unit_sek / best_alt_unit_price_sek × 100` — kronor per unit cannot be compared between rows (0,62 kr/st against 8,20 kr/kg says nothing about which is the better buy), percent can. It is **not** `discount_percent`, which is the store's framing against its own ordinarie and ranks nothing. It had a column of its own in one draft and then a sentence, and it is now neither: every row under "Värt att köpa" is best by construction, so the sentence restated the heading on every row while competing with the **span bar** to be the row's single score — and it won by sitting first and being biggest, which is the wrong winner (the bar answers the question the reader arrives with: *is this a good price*, not *is this the right shelf*). A list expresses its ranking by being a list. **WORSE and UNKNOWN keep their sentence** — the span bar is the TIME axis and cannot say another link is cheaper right now, and UNKNOWN's names the gap plus its fix. **The butik moved into the meta line** when the sentence went: it used to close that sentence, and it is the way OUT to the store's own page. **The span bar comes FROM THE DEAL ROW** (`lowest_unit_price_sek`/`highest_unit_price_sek`, v0.50.0), never from `/stats`: the bar and the `timing` verdict must read the same 84-day window, and the stats period is whatever the Prisutveckling picker last held — a 4-week pick there once made the bar and the "har varit X billigare" note state opposite things about one row. When `high <= low` NO bar is drawn — a bar without a span would claim a position that does not exist, the same rule `stats.py` follows when it returns `change_pct = None` rather than 0. **The offer's villkor (`offer_details`) sits beside the product name** (v0.53.1), not at the row's foot: it is a condition on the price printed to its right ("2 för 99,00" is not a per-unit price you can walk up and pay), and the foot is the last place a swept row is read. It wraps rather than being shortened to a badge — "Max 2" drops which condition applies.

- **The korgremsa is derived from the rows the list shows, and its store pills ARE the filter.** Pill counts, subtotals, the total and the closing sentence all come from the same array the list renders, so a pill cannot promise a round the list does not hold, and no butik can be missing (which would make its rows unreachable). A pill filters client-side on `store_name` and stands beside the header's scope switch, which is `store_type` on the server — the two compose. With a filter active the heading, the sums and the closing sentence all change, or the strip lies.

- **The scope switch is one state with two controls** (the header segment and Produkter's chips) and survives page changes in `sessionStorage`. It filters Att köpa server-side (`/deals?store_type=`) and Produkter client-side via `/stores`' `store_type` per slug.

- **Att köpa (Erbjudanden until v0.47.0) is grouped by whether the offer is actually the cheapest way to buy the product, not by when we checked.** The three-way split — **BEST** (`unit_price_sek <= best_alt_unit_price_sek`), **WORSE**, and **UNKNOWN** (either is null — no amount on the link, or the product has no other link) — **is computed in `domain/deals.py` since v0.41.0** and rides the wire as `verdict` + `savings_per_unit_sek`; the portal's `classifyDeal`/`dealSavings` are READERS of those fields, never a second derivation (the buy-list email needs the identical judgement, which is exactly the Gotcha-4 setup). BEST + UNKNOWN render under "Värt att köpa" ranked by the **kr/unit margin over the next-best link**; WORSE goes in a collapsed `<details>`, least-bad first. The discount % is the STORE's framing and ranks nothing — 30 % off a bad price is still a bad price, and ordering on `checked_at` put exactly those rows on top. UNKNOWN rides with the buyable ones deliberately: it is not *known* to be bad. The "Köpvärda erbjudanden" stat counts BEST only (tooltip carries the full breakdown). **`GET /deals` still orders by recency and still returns every offer** — the ranking is a view, and `find_deals`/MCP consumers keep their contracts (they too now carry the verdict). All three former copies of the deal query (admin route, service, scheduler summary) collapsed into `deals.current_deals`; the admin copy's recency-dedupe had already drifted — it kept showing a link's superseded offer after the latest point had none, which the latest-per-link JOIN makes impossible. **Both queries filter on `is_active` (v0.41.2)** — the deal AND its alternatives: an inactive link's frozen last price is not a shelf anyone can buy from, and letting it win as `best_alt` flipped a genuine BEST to WORSE, which the buy-list email then dropped (pinned by a real-Postgres test in `test_deals.py`). **The deal row's product name is a button into the price-history modal (v0.42.0)** — the same `showPriceHistory` modal as Produkter (the /deals wire already carries `product_id`/`product_name`/`unit`; name + unit resolve from the client-side `allDeals` cache, NOT `allProducts`, which may never have loaded). Only the NAME is the target — no whole-row fallback, because the butik cell is already the link OUT to the store; a hover-triggered graph was rejected outright (no hover on the phone in the aisle, and a Chart.js render + API call per swept row).

- **The product ROW is the Länkar button, and each removed action went where its context already lives.** Five buttons per row (Länkar / Länka / Historik / Redigera / Ta bort) meant 75 controls on a 15-product screen, two of which differed by one letter while doing different things. Now: the row opens the links panel, which is what the table leads into — **the visible affordance is the product NAME, a real `<button>`** (focusable, Enter works), with the rest of the row as a quiet convenience target; **the Åtgärder cell is excluded from that target** (`td.row-actions`), because empty space beside two buttons that silently opens a panel is an invisible third button, reported as a graphical bug within a day of shipping v0.34.0. **Länka butik lives IN that panel** (the dialog stacks above it via `#modal-link-store { z-index: 210 }` and refreshes it on save); **Ta bort lives in the edit dialog** beside the fields it destroys, and its confirm names the product and counts the links + history going with it. The card header keeps ONE primary button (Snabbtillägg, the 95 % path); Ny produkt / Exportera / Importera sit in a `<details class="menu">` overflow. **The links panel follows the same shape (v0.34.2):** its row keeps Redigera + Kontrollera nu, and deleting a link lives in the "Redigera länk" dialog as **Ta bort länk** — "Avlänka" was jargon rather than Swedish, and a third button on every link row for something done twice a year. Its confirm names the butik and the package, because "butikslänken" is ambiguous with three of them on screen. **Do not put such a menu inside the products table:** `#products-table-container` is an `overflow-x: auto` box, which computes `overflow-y` to `auto` and clips the last row's dropdown. **The row's badge (erbjudande / saknar mängd / en butik) sits beside the NAME (v0.53.1)** — it is a property of the product, and on the right it was right-aligned against the price column, which read as a statement about the butik standing next to it and moved horizontally from row to row with the price's width.

- **The product list filters in the browser; `allProducts` is ALWAYS the full list.** `loadProducts` fetches `/products` unfiltered and `renderProducts` filters between the array and the DOM. Before, the search round-tripped per keystroke *and assigned the result to `allProducts`*, so the global list silently meant "whatever the table is filtered to" — which is what the watch dialog's product `<select>` reads. Facets (kategori, butik, täckning as `<select>`s; omfång, status = har erbjudande / saknar pris / **trasig länk, v0.40.0** and sort order as CHIPS since v0.47.0 — **"saknar mängd" left this row in v0.53.1**: the field that closes that gap is on Fel & luckor, one row per link, saved in place, so a chip here only narrowed a list you then had to leave anyway. A stored `needs_amount` status is cleared on restore rather than filtering with no chip on screen to switch it off) are built **from the data** with their counts, so a filter can never be offered that returns nothing. The chips are delegated and the four selects bind by id at top level — `test_static_gates.py` gates those four ids (it asserts the COUNT too, so moving a facet between the two forms is a deliberate edit, not a silent one). **Trasig länk is DERIVED per read, never persisted:** `domain/link_health.py` is THE judgement (the link's last 3 non-blocked `check_attempts` all failed — one "ok" clears it by construction, same self-clearing shape as `quantity_mismatch`), every link row carries `is_broken`/`broken_detail` (both `_link_payload` in admin.py and `get_links_for_product` in service.py — the Gotcha-4 twins — resolve through the one `broken_links` query), the facet option appears only with a hit count ("Trasig länk (2)") and the links panel shows a badge whose tooltip carries the last HTTP status. **BLOCKED attempts are invisible to the judgement in both directions** — a wall neither counts as a failure nor interrupts a streak, because an ICA challenge evening must not paint 44 valid links as broken and invite their deletion (the v0.19.0 misread). Deliberately no auto-retirement and no URL-repoint action: the URL is the link's identity, so a moved page is a new quick-add link plus Ta bort länk on the old one. **The täckning facet asks the inverse question — "vad jämför jag INTE?" (v0.38.0).** The whole point of the tracker is comparing the same product across chains, so the interesting rows are the products that exist at one chain and not the other. It keys on **`store_slug`, not `store_name`** — two ICA butiker are two links under ONE chain, and `store_name` carries the butik label ("ICA Maxi Sandviken"), so a name-keyed gap would ask the wrong question. It **requires at least one link** (a product with none is not a comparison gap but a half-finished product; "Saknar pris" is that filter), and it composes with the existing butik facet: "Butik: Willys" + "Saknar ICA" is the query stated exactly. **`STORE_OWN_BRANDS` (in `admin.html`, keyed by store slug) is what keeps it usable, and it is MEANT to be extended** — an ICA-branded product will never be at Willys, so without the exception it is a gap that can never be closed and sits at the top of the list forever. On live data it hid 5 of 11 rows in "Saknar Willys", all of them ICA-branded. Own brands are excluded only from FOREIGN chains: an ICA-branded product with no ICA link is a real gap and stays. Matching is exact and case-insensitive, so "ICA Basic" needs its own entry — it inherits nothing from "ICA". Each option carries the count it would show ("Saknar ICA (4)"), smallest gap first, which is why no threshold is needed: "Saknar Lyko (22)" is self-evidently not a comparison gap. Chains with no gap are not offered at all — same rule as the other facets. The "Sortera: butiksordning" chip uses `domain/categories.py`'s walk order, read back off the server-injected `#edit-product-category` options — **a view of THE list, never a second copy** (uncategorised sorts last). State lives in `sessionStorage`, **not in the hash**: `currentPage()` parses the whole fragment as a page name. `/products?search=` stays for the REST API and MCP. The wiring binds by element id at top level, so a renamed control throws mid-load and leaves the whole page inert — `test_static_gates.py` gates those ids against the markup.

## The links panel and categories

- **The links panel's "Pris" cell is what you PAY, with the ordinarie under it (v0.62.1).** That table has no erbjudande column, and it printed `price_sek` — the ordinarie — beside a jfr-pris computed from coalesce(offer, price): a link on campaign read "129 kr · 0,68 kr/st" (= 90/132), one link whose two cells disagreed by the whole discount with nothing on the row mentioning a campaign. Both Gotcha-4 twins (`_link_payload` in admin.py, `get_links_for_product` in service.py) now carry `effective_price_sek`, **and the column SORTS on it** — a cell showing one number under an order keyed on another puts rows where the reader cannot see why. The **JS `effectivePrice()` twin was deleted in the same change**: once the payload carries the domain's answer, a local coalesce is a second definition by construction (gated). Same release fixed the two formatters this cell had escaped — `kr()` and `unitKr()` instead of raw concatenation, which printed "129 kr" and "0.68 kr" with an English decimal point (the v0.54.0 "79.9 kr" bug, in the one table it had survived in).

- **`Product.category` is a fixed ordered enum (v0.20.0–v0.21.0):** the 10 grocery-section values and their in-store walk order live in `domain/categories.py` (THE list). `normalize_category()` coerces free text / an old LLM guess to a canonical value or None (keyword map; `"ost"`/`"fil"` ordered last so they don't swallow `"kosttillskott"`/`"filmjölk"`); `category_sort_index()` is the aisle-order sort key (ready for a future shopping-list sort; the product list still sorts by name). The UI `<select>` is server-injected from the list in `render_admin` (no second copy) and `test_static_gates.py` guards the `<!--CATEGORY_OPTIONS-->` placeholder. Server normalises on create/update/import. Free text is gone; "Kött, Chark & Deli" merged the old meat/chark/fish split.

## The price-history modal

**The price-history modal is the per-product view, it has an ADDRESS, and it stays a modal on evidence (v0.54.0; addressable v0.56.0).** It opens from Att köpa, Produkter and **Prisutveckling (v0.58.0)**, and it lives at **`#/<page>?produkt=<id>`** — `currentPage()` splits the fragment on `?`, opening it PUSHES that hash, and the hashchange is what opens the dialog. One mechanism gives both things it lacked: a URL you can paste, and a back button that closes it instead of leaving the app. **The hash is THE state and nothing may call `showPriceHistory` directly** (gated in `test_static_gates.py`, both halves): a second way in opens the drill-in with the address bar naming the page behind it, and a × that merely hides the dialog leaves the pushed entry so the URL names a product nobody is looking at. `closePriceHistory` goes BACK when we pushed the entry and rewrites the hash when we did not — a cold deep link has nothing behind it, and `history.back()` there leaves the app. Init AWAITS the product list before opening a deep link, because the header is the only place the product is named. **Escape closes the read-only drill-ins only** (history + links panel, topmost first): the form dialogs hold typed input, and a quick-add confirm discarded by a stray keystroke costs a store fetch to rebuild. **Each entry point is a rendered `data-` attribute plus a delegated handler written far apart in the file, and BOTH halves are gated** (`data-deal-action`, `data-stats-product`): half a pair renders a product name that looks exactly like the working one and does nothing when clicked, which no runtime test can see — the drill-in never reaches the API. **And a per-page fetch keys on `renderPage`'s page CHANGE, not on the hashchange that called it (v0.58.0):** the drill-in lives in the hash too, so opening and closing it over Prisutveckling fired two hashchanges without leaving the page and re-ran `/stats` — the heaviest query in the app — twice, to repaint a table the modal is covering, with the modal's own two fetches queued behind it. Nothing looked wrong; it was slow exactly when a reader clicks. Arriving from another page still refetches, which is what "fresh on each visit" meant.

**BOTH chart modes plot the EFFECTIVE price, and the wire carries it (v0.62.1).** kr/enhet has always been `unit_price_sek`, computed from coalesce(offer, price); "Absolut pris" read `price_sek` and therefore drew a campaign day at the ordinarie — under the hollow ring announcing the campaign, contradicting the mode beside it, the summary strip above it, the buy list and the shelf. A price history whose two readings of one row differ by the whole discount is worse than no chart: nothing raises, and the wrong number is the one a reader can check. `price_history_rows` now emits `effective_price_sek` (`pricing.effective_price` — THE definition; a client-side coalesce would be the second one), `price_sek` stays for the ordinarie, and an offer point's tooltip names it ("90,00 kr (ordinarie 129,00 kr)"). Both halves are gated in `test_static_gates.py` — the field selection AND `groupHistoryByLink` carrying it onto the observation, because selecting a field nothing copies draws an EMPTY canvas, and no runtime test reaches this modal.

**A routed page was proposed for this and REFUSED on a measurement (2026-08-13):** `renderPage` toggles `.app-page` visibility, so the hidden page leaves the flow, the document collapses and the scroll resets — a product PAGE would return the reader to the TOP of Att köpa, the one list swept top to bottom while standing in a shop. The other selling points did not survive contact either: the graph gets no wider below ~1500 px (`.modal-large` caps at 960 px and a 280 px sidebar eats what the wider container gains), and on the phone the modal is already a 92vh bottom sheet. What was genuinely missing was the URL and the back button, which cost about a hundred lines instead of a release, and kept the content that v0.54.0/v0.55.0 had already built and tested. The summary strip carries only things the fetched rows literally contain — a minimum, a maximum, a count, a timestamp — plus **förändring READ off `/stats`** when that payload happens to be loaded and simply omitted when it is not: change over a period is `stats.py`'s definition (carry-forward, a baseline from before the window, an em dash rather than 0,0 % on one observation), and a second one computed in JS would drift from it exactly as Gotcha 4 predicts. Same shape as the deal row reading `verdict` instead of deciding it. **Its span bar is labelled "Prisläge i perioden" on purpose:** this app has three windows that could each be called "spannet" — the deal row's 84-day floor, the statistics period, and the modal's own 90 days — and an unlabelled bar would silently pick one. `buildBestAvailableSeries` is kept though nothing draws it: it is THE honest carry-forward walk across links, and the day an envelope is wanted again it should be reused rather than rewritten.

## Fel & luckor

**Fel & luckor owns the whole to-do list, and every count on it opens a list that is ON it (v0.53.1).** The counters used to be a way OUT: "Länkar utan mängd" set a facet on Produkter and navigated there — putting the number on one page and the work on another, while the product table holds no affordance that closes any of it. Now the two counts with a per-row action scroll to their own section (`data-issue-goto`), Produkter lost its **Luckor** chip (a stored `needs_amount` filter is cleared on restore — an invisible filter with no control to switch it off is worse than a stale one), and **"Produkter i bara en butik" became a section, not just a figure**: the products whose price cannot be compared against any other chain, with the chains they have and the ones they lack as chips, and a **+ Länk** button opening the link dialog directly. Two rules make that list worth reading: it keys on **`store_slug`** (the chain) rather than the butik label — /stats counts this by label, so an ICA Maxi + ICA Björksätra product counted as two "butiker" while being comparable nowhere, which is why the counter above it is now derived from THIS list (one number, one list, no drift) — and it **excludes own brands** via `missingFromStore`, the v0.38.0 rule, without which an ICA-branded product sits at the top forever as a gap that can never be closed. Candidate chains are restricted to the product's own `store_type`: a bag of coffee does not "saknar Apotea". The two remaining figures (aldrig kollade, äldsta kontroll) are deliberately NOT clickable — they have no per-row action, and a box that looks pressable and does nothing is worse than a plain figure.

**Fel & luckor separates SILENT errors from gaps, and that separation is the page (v0.47.0).** A gap announces itself — a jfr-pris is missing, a cell is empty. A silent error does not: the check reports `ok`, the price is plausible, and nothing anywhere else in the interface reveals that the figure is wrong. That is precisely the miss that produced `domain/validation.py` (ICA's campaigns invisible for weeks while every check said "ok"), so the silent errors sit at the TOP and in red, before the counters; the gaps keep amber below. It is also the answer to "how do I see a parser failure without digging in the logs": **the log shows EVENTS, this page shows STATE** — a tier regression from Thursday has rolled out of the ring buffer by Monday, while the state stays here until a successful check clears it. Four blocks, all from data the domain already computes: `data_quality.tier_regressions` + `.unit_price_mismatches` (the red band), the four `coverage` counts, `link_health`'s broken links, and the links with no mängd — each of the last with an **inline amount field and Spara**, because sending the reader to a dialog three clicks away is how a six-item list stays a six-item list. The consequence text per tier regression is DERIVED from `expected_source` (`TIER_IMPACT` in the template): `ica_page → jsonld` says nothing to anyone who does not know the codebase. **The raw pair itself is ADMIN-ONLY since v0.56.2** — it was the last untranslated machine name in the interface (everything else on the wire — `verdict`, `timing`, `outcome`, `store_slug` — is rendered in Swedish) and it was drawn in the row's alarm red at weight 600, so the loudest word in the row was the one a reader cannot interpret, sitting above a sentence in plain text that they can. It stays for the admin because it is the ONE pointer to which extractor tier degraded, which is where the fix starts. Noise control, not secrecy: the values are in `/stats`, which every reader may GET by design. **Loggar now says what it is** (v0.56.2): events here, state there, with the way across — the distinction was written down only in the code, so a reader could conclude from an empty ring buffer that nothing was wrong. Its ROWS deliberately link nowhere: a log line has no identity, and resolving one back to a link would be text matching in the direction where a mistake is most expensive. **A store's printed figure is labelled with the STORE's measure, not the product's (v0.58.2).** The mismatch row drew `unitKr(printed, unit)`, so a Willys kr/kg jämförpris on a per-styck product read "97,78 kr/st" — the wrong measure stated with confidence, in the row whose whole job is to name what is wrong. `printed_unit` rides the row (None when nothing recorded a measure, which is most of them) and the cell renders through `storeSaysKr`, bare kronor on unknown. A reported row's measure is either equal to the product's unit or UNKNOWN — a positively different one is vetoed upstream — and those two are not interchangeable on screen. This was considered and DECLINED in v0.58.1 on the argument that the row's premise makes them equal; the premise holds only when a measure was recorded, and prod produced the counterexample within hours. Both renderings of a store-printed figure are now gated together — the v0.58.1 gate covered only the links panel, which is how this one shipped.

**Nothing here may be dismissible** — no flag is persisted, so a dismiss button would only hide an error that is still running; a successful check from the right tier, or a corrected amount, removes the row by itself. The band's foot ("blockerade hämtningar räknas inte som fel här — en vägg är butikens tillstånd, inte vårt") is load-bearing: without it an ICA wall reads as a breakdown and invites deleting perfectly good links. The sidebar badge counts the SAME rows the page lists, derived from the lists' lengths, and turns red the moment a silent error is among them.

## Bevakningar

**Bevakningar groups on what the reader can DO, and one group exists because it was invisible (v0.53.0).** A watch row has always answered "how close is it?" with a bar. What it could not answer is whether the question has an answer at all: a target below every price the product has ever been observed at is not a strict watch, it is a watch that **cannot fire**, and it rendered exactly like one that is merely waiting — forever, silently, which is the same failure class as the ICA campaigns `domain/validation.py` exists for. Four groups, in this order: **under målet nu** (buy if you need it) · **inom räckhåll**, closest first by the gap as a PERCENT of the target (the groups mix units — 0,29 kr/l and 4,00 kr/kg say nothing about which is nearer) · **larmar inte som det är satt** · **utan mål** (alarms on any offer — a setting, not an omission). An empty group prints nothing; an empty "larmar inte" heading would read as a warning where there is none. The count of unfireable watches also rides the page's own summary line, for the same reason.

- **The evidence is `domain/deals.observed_spans`, made PUBLIC rather than copied** (it was `_floors`). Same window (`PRICE_LOW_WINDOW_DAYS`), same ≥2-observations rule, same "inactive links count". A second hand-written floor query would drift from the buy list's within a release (Gotcha 4) and the two disagreeing about what a product has cost would be invisible until an alarm quietly never went off. `/watches` carries `lowest_unit_price_sek` / `highest_unit_price_sek` / `lowest_seen_at` / `lowest_store` / `span_window_days`.

- **Only a kr/enhet target may be judged against the span, and that is a hard rule.** An absolute `target_price_sek` is a PACKAGE price; a 100-pack and a 20-pack of one product share a kr/tabl. and have wildly different kr, so placing one on the other's axis is the g/kg class of error (it pinned a cheap link to the expensive end of the bar in the first render of this feature). An absolute target is never called unreachable and never gets a marker — it keeps the distance bar it always had, which says less and is true. **Both targets stay named in every row's meta line** either way: the scheduler alerts on whichever is set, and a target the page does not show is an invisible trigger (v0.27.0).

- **The target is a SECOND mark on the bar, deliberately not the same one as the current price** (`.span-target` vs `.span-marker`) — a reader who confuses them reads the row backwards. A target outside the span gets an edge arrow rather than a tick clamped to 0 %: clamping would draw it AT the floor and quietly deny the very problem the row is reporting.

*From the release index, removed by the information-layout move:* `PUT /watches/{id}` keys on `model_fields_set`, so a SENT null clears a target while an absent key is left alone, and the dialog sends every field on save (v0.27.0; before it a target was settable, never removable). Both targets are shown, because the scheduler alerts on `target_price_sek` AND `unit_price_target_sek`, and showing one leaves an invisible trigger on a watch restored from a backup.

## Accessibility

**A dialog announces itself, and `openModal` is THE way one is opened (v0.56.1).** The portal is read by a READER role — the household the Entra gate lets in — and v0.29.0 exists because one of them actually logged in, so this is real usage rather than a hypothetical audience. Four rules, each of which fails invisibly (nothing on screen looks different when they rot, which is why all four carry gates in `test_static_gates.py`):

- **`aria-modal="true"` is a promise markup cannot keep alone.** It asks assistive tech to ignore everything OUTSIDE the dialog, so focus must BE inside it — otherwise the reader is parked on a button their own reader can no longer describe. The attribute and the focus handling ship together or neither should: **`openModal(id)` is the single entry** (ten call sites used to set `display` by hand), a Tab handler keeps focus in the topmost dialog, and `closeModal`/`syncHistoryToHash` hand it back to the opener. **Focus goes to the first VISIBLE FIELD, and both words were paid for** (v0.56.1/v0.56.2, both found by rendering the page rather than reading it): the × sits in the header and wins a plain DOM-order query, which lands the reader on "close" and makes Enter dismiss what they just opened; and `:not([disabled])` does not mean visible — for a READER the links panel's first button is "+ Länka butik", which `.admin-only` hides, and `.focus()` on a `display:none` element is a **silent no-op**, so focus stayed on `<body>` outside a dialog claiming `aria-modal`. Both queries filter on `offsetParent`, the same test the Tab trap uses, so the two agree on what "in the dialog" means. The handback is equally untrusting: if `.focus()` on the opener does not take — the overflow menu closes while a dialog is up, and a button in a collapsed `<details>` cannot take focus — the `<summary>` gets it instead. **Detect the outcome, do not enumerate the causes**; both of these failures are silent by nature. Stacked dialogs keep the OUTERMOST opener: "Länka butik" over the links panel must not send focus back into a panel that is itself closing.

- **A label that merely sits beside its input names nothing.** Both valid shapes are accepted — `for=` resolving to a real id, or the control nested inside the label (how the checkbox rows are written). `aria-labelledby` is checked against real ids because a typo'd reference is WORSE than none: the dialog is unnamed either way, but the attribute claims otherwise.

- **The toast's timer is load-bearing.** It is the only feedback several actions get. `clearTimeout` before re-arming, or the next toast inherits the previous deadline — the import summary ("Import klar: N skapade, M bevakningar"), one of the few toasts carrying counts recoverable nowhere else, was the likeliest casualty because dwell was a fixed 3 s regardless of length. Dwell now scales with reading time, an error outlives a success, and the text is blanked before it is set (`role="status"` announces a CHANGE, so the same message twice was silent).

- **Rendering is how this class of bug is found.** `node --check` says the file parses; it cannot say the × was focused. The recipe — assemble shell + fragments, stub `window.fetch`, drive it in the Chromium in `~/.cache/ms-playwright/` — caught two defects in this very change. Note the trap it also caught: a control on a hidden `.app-page` cannot be focused, so a probe that opens a dialog from another page tests nothing.

## Design handoffs and what review refused

**Design handoffs live outside the repo, and what a review REJECTED is the part worth writing down.** `design_handoff_*/` is gitignored (v0.53.0; "3a" in v0.47.0 was likewise never committed) — an interactive prototype is a reference for one round, not source, and its mock arrays invite being read back as facts about the app. The 2026-08-11 review ("förenkling") was adopted in the two places above. **These parts were refused, and the reasons outlive the handoff:**

- **A "silent error" row showing the shown price struck through and the true one beside it, with a "Byt källa" picker.** The app does not know which figure is right, and says so on purpose: a tier regression is cause-neutral (the store changed shape, OR the link has not been re-checked since an extractor improved) and a jämförpris mismatch means "either the price or the amount is wrong". Presenting one number as truth is a claim `domain/validation.py` refuses to make, and a per-link extraction-source override contradicts the ladder itself — the tier is code, `EXPECTED_SOURCE` is derived from the registries.

- **Collapsing Produkter's facets** to search + trend chips: it drops the butik filter, the four status facets (incl. **Trasig länk**, v0.40.0), the `categories.py` walk-order sort, and the 10-value category enum (the proposal's "Livsmedel/Apotek" is `store_type`, which is the scope switch, not a category).

- **Losing Snabbtillägg / Exportera / Importera from the Produkter header**, and moving the links panel behind a row overflow menu — the row IS the links button, and Exportera is THE backup.

- **Modelling a watch with ONE target** (→ watches-page bullet), **shortening `offer_details` to a badge** ("Max 2" for "Välj & blanda! 2 för 99,00" — the price only exists under the condition, v0.41.2), **making the deal row's butik plain text** (it is the link OUT), and dropping the `in_stock` marking (v0.50.0: mark, never hide).

- **Everything in it is desktop-only** (fixed 160 px + 160 px + price columns at a 1440 preview). Att köpa is read in the aisle; the phone layout is not a later concern for that page.
