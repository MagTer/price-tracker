# Store extractors

Store knowledge: how each store publishes its prices, and how the ladder reads them. Getting the request through to the store at all (ledger, fetcher, breaker, scheduler) is the `store-fetching` skill; what is done with a price once read is `price-judgements`.

Moved verbatim from `CLAUDE.md` at `88e99e9` by the information-layout move (`git log -- .claude/skills/store-extractors/SKILL.md` names the commit). A pointer of the form "→ X bullet" names a bullet by its subject; it may sit in another project skill — `AGENTS.md` lists all four.

## Campaign prices and store links

- **A campaign is ORDINARIE + OFFER, identically in every store (v0.25.2–v0.25.3):** `price_sek` is the ordinarie price, `offer_price_sek` is what you pay now, `offer_type="kampanj"`. Both extractors used to be wrong, in opposite directions. **Willys API (corrected again in v0.41.1):** `priceValue` is ordinarie and **the per-unit campaign price is `potentialPromotions[].price.value`** — `savingsAmount` is the TOTAL saving over the promotion's `qualifyingCount`, NOT a per-unit discount. v0.25.2's `priceValue - savingsAmount` rule was verified on a single-unit campaign (21.29 − 3.39 = 17.90 = `price.value`), where the two coincide — on a multi-buy it invented a price that exists nowhere (Bryggkaffe, 2026-07-29: ordinarie 67.90, "Välj & blanda! 2 för 99,00", savingsAmount 36.8 = 2×67.90 − 99; the subtraction recorded 31.10 while the shelf charges 49.50/st, and 31.10 ranked as an absurd bargain in every kr/unit view). The subtraction survives only as the fallback for a saving with no promotion price **and no multi-buy in sight (v0.41.2)**: any promotion with `qualifyingCount > 1` refuses the fallback wholesale — a multi-buy whose promotion price is missing or unparseable gets NO offer, never a guess — and a `price.value` arriving as a string is parsed rather than silently demoted to that arithmetic. `offer_details` carries the store's own `cartLabel` ("Välj & blanda! 2 för 99,00") so the multi-buy CONDITION is visible — **in the portal's price cell too, not just the email (v0.41.2)** — and a promo price with no label gets NO details ("Spara 36,80 kr" beside a per-unit price would claim the TOTAL saving per unit); promo prices are quantized to öre ("3 för 95" arrives as 31.666…), several priced promotions pick the HIGHEST (smaller claimed saving is the safer error, Lyko's rule), and an offer at or above ordinarie is refused wholesale (v0.32.1). The even earlier code ADDED the saving, inventing a "regular" price that appears nowhere in the API. NB the `/erbjudanden/offline-*` pages are NOT product pages — they are butiksblad offers served from `/axfood/rest/v1/offline-product/{storeId}/{code}` (store-scoped, "olika sorter", jfr-pris as a RANGE) and are not trackable links. **JSON-LD pharmacies:** the struck-through ordinarie hides in the offer's `priceSpecification` — `ListPrice` (Apohem) or `StrikethroughPrice` (Kronans), dict or list, http or https — and counts only when it is **higher** than `offers.price`; the old code kept the current price as `price_sek` and discarded ordinarie, so a pharmacy sale never surfaced in "Erbjudanden". A `UnitPriceSpecification` bearing only the jfr-pris is not an ordinarie. **Willys' jämförpris MEASURE comes from `comparePriceUnit`, never from `comparePrice` (v0.58.2).** `comparePrice` is a bare amount — "97,78 kr", verified on six live products 2026-08-17 — and the measure sits in its own field beside it ("kg", "l"). The extractor parsed a `/(\w+)` suffix out of the string instead, which therefore **never matched once**: every Willys point ever written carried no `comparison_unit`, so `pricing.printed_measure` answered None and the validator judged every Willys jämförpris with no measure veto. Harmless for as long as `Product.unit` happened to BE the printed measure, and wrong the first time it was not — a middagskit compared per styck against a kr/kg jämförpris surfaced as a 73 % silent error with both numbers correct. Stored as "/kg", not "kg": the bare token matches no marker in `PRINTED_MEASURE_MARKERS` and would read as "no measure recorded". The suffix regex survives only as a fallback. **The general trap: a field that has always been empty looks exactly like a field that is correctly empty** — this one hid behind the validator's own "unknown keeps judging" rule, which is right and which is what made it silent.

**kr/unit is unaffected by all of this** — it ranks on `effective_price_sek = coalesce(offer, price)`, which is the price paid either way.

- **`ProductStore.store_label` (v0.6.0)** is the link's optional display store name ("ICA Maxi Sandviken") for chains that price per physical butik — two ICA butiker are two links under the ONE chain-level `Store` row (whose slug drives the extractors; never add per-butik Store rows). `domain.models.link_store_name` (label wins, chain name is fallback) is the single display rule; every store-name emission (links, history, deals, emails, MCP) goes through it. Quick-add suggests the label from the URL's `/stores/<id>/` segment (`quickadd.KNOWN_STORE_LABELS`), and for butiker in `quickadd.SIBLING_STORE_GROUPS` it also offers to create the sister-butik links in the same confirm (v0.7.0) — siblings are created optimistically and left for the scheduler (v0.19.0 stopped fetching them inline: sister butiker share ONE `store_id`/host, so an inline check per sibling was the same-host burst that tripped ICA's WAF, and under the block-aware fetcher a rate-limited fetch is indistinguishable from an absent page, so it would wrongly delete valid siblings). Both tables are per-instance operator config since v0.8.0: env `QUICKADD_STORE_LABELS` / `QUICKADD_SIBLING_GROUPS` (JSON), in-repo defaults are Magnus's butiker, malformed JSON warns and falls back — the repo is public/MIT and a second instance sets its own.

## The extraction ladder

- **The extraction ladder is structured-only, and a store saying "gone" ends it (v0.66.0, decided with Magnus 2026-10-19).** `PriceParser.extract_price` runs store API → store page-state → JSON-LD and stops. A miss is an honest `no_price` whose `raw_response["reason"]` (`result.no_price_reason`, THE reader) becomes the `check_attempts.detail` that `link_health` hands Fel & luckor. **`domain.result.ProductGoneError`** is raised where the store states it: the Willys API's 404/410 for the code (`{"errorCode":"NOT_FOUND"}`; the SPA shell still answers 200, so no lower tier can tell), and a JYSK page whose ProductGroup lacks the URL's `?article=` or whose single Product carries another sku. The ladder stops on it with source `product_gone` and detail "produkten finns inte hos butiken (…)", and the Fel & luckor hint matches that text as well as an HTTP 404/410. **Why there is no model tier:** measured on prod 2026-10-19 across every price point ever written (~1 900), the LLM fallback answered 8 checks, all on the two links above, and all 8 were wrong — 135 kr recorded as ordinarie at a −55 % rea, the EU-Omnibus line "Lägsta pris 30 dagar" stored as villkor, and 49,90 kr / 89,90 kr/kg that appear nowhere on the page. Because the cascade always answered, the checks said "ok" and `link_health` never flagged either dead link; only the tier-regression alarm saw them, and it read like a broken extractor. **Enrichment went on the same review:** its pharmacy offers were JSON-LD's own (`Spara 39 kr` is the jsonld extractor's wording, and the unenriched points beside them carry the same offers), leaving a jämförpris on about ten points as its only contribution. **Rejected alternatives, with the reason:** (1) keep the fallback but require every number it returns to appear in the page text — it would have stopped the Willys point and not the JYSK ones, whose numbers were real but belonged to a sibling variant; (2) keep it and mark its points uncertain, excluded from floors and the buy list — a second rule every query must honour, for a tier with no measured value (the Gotcha-4 drift shape). Quick-add's LLM identity step was unreachable for every supported store (each has a structured tier before it) and is gone with the rest. **If a model ever returns, it starts from a measurement that it adds value, never from a page it could read.**

*From the release index, removed by the information-layout move:* the v0.66.0 cleanup deleted from prod, on 2026-10-19, the 8 LLM-priced points, the two dead links and the NORA product; the deleted rows are saved as JSON in `~/price-tracker-backups/2026-10-19-llm-cleanup.json` on the dev box, outside the repo. Since v0.41.3 `extraction_source`/`offer_type`/`offer_details` are clamped to their columns instead of failing the write.

## Per store

- **Rusta is read from `window.CURRENT_PAGE`, not from its JSON-LD (v0.31.0):** Rusta (an Avensia Nitro storefront) server-renders both, but the JSON-LD carries only the CURRENT price — at a rea (verified live 2026-07-27: Hängstol Sorrento, current 1899 / original 2999) extracting it would record the campaign price as `price_sek`, the exact ordinarie/offer inversion v0.25.2/v0.25.3 fixed elsewhere. `domain/extractors/rusta.py` parses the CURRENT_PAGE hydration JSON from the already-fetched page: `original` → `price_sek`, `current` → offer when lower, `comparisonPrice`/`comparisonUnit` → the printed jfr-pris (absent from JSON-LD entirely), `stock` → in-stock, and `subTitle` ("50 ml Invisible Black & White") → package evidence via `parse_package_from_name`. The node is verified against the URL's trailing article code (root or `variations[]` — color siblings share one page); a mismatch returns None rather than recording a foreign product at 0.98 confidence. **The extractor lives in THE `_HTML_EXTRACTORS` registry in `domain/parser.py`** (`get_html_extractor` — same sharing contract as `_API_EXTRACTORS`, used by the price ladder AND quick-add preview): a store-HTML extractor parses the page the pipeline already fetched, makes no HTTP calls of its own, needs no ledger slot and can never raise `StoreBlockedError`. Ladder order is store-API → **store-HTML** → JSON-LD, and nothing after (v0.66.0); every Rusta parse failure degrades to JSON-LD (right price outside campaigns), never to a failed check. Rusta runs in interval mode (72h default, no offer weekday) and its sale prices surface only via this tier — treat "Rusta rea not flagged" as "CURRENT_PAGE changed shape", and check the `Page-state extractor` WARNING in the logs.

- **Clas Ohlson is JSON-LD *plus* its BEM price markup (v0.32.0):** same blind spot as Rusta — the JSON-LD carries only the current price (verified live 2026-07-27: Braun 44-6051, JSON-LD 499 while the page shows ordinarie 999,00) and no jämförpris — but hybris renders JSP markup, not hydration state, so `domain/extractors/clasohlson.py` reads the stable BEM price section instead: `product__old-price`/`product__discount-price` at a rea, `product__comparison-price` ("(1,91/st)") otherwise, anchored on the SKU token in the container class (`product__normal-price 446051000` — the URL's `/p/` digits must prefix it, which is what keeps carousel price blocks out). It **COMPOSES the shared `JsonLdExtractor`** for identity/availability/price rather than re-parsing, and self-checks: markup price ≠ JSON-LD price → WARNING + None, and a markup that adds nothing (no rea, no jfr-pris) → None — plain JSON-LD answers both. NBSP thousands separators ("1 290,00") and `&nbsp;` entities are handled. `extract_metadata_from_html` is deliberately None: Clas Ohlson's JSON-LD names carry the package text ("…, 94-pack"), so quick-add's JSON-LD tier already previews everything.

- **Lyko is read from `window.CURRENT_PAGE`, and its `comparisonPrices` is NOT a jämförpris (v0.37.0):** Lyko runs the same Avensia Nitro platform as Rusta and has the same JSON-LD blind spot (verified live 2026-07-29: N.C.P. Hand Wash 201 publishes `"price": "58"` while selling at 80 % off an ordinarie of 290), so `domain/extractors/lyko.py` reads the hydration state. **But the field that carries kr/liter on Rusta carries something else entirely here**, and a copy-paste would invent campaigns: Lyko's `comparisonPrices` is a LIST of prices to compare against, each with a `type`, and only `ordinary` ("Tid. pris") and `withoutCampaign` ("Utan kampanj") are an ordinarie the store itself charged. **`recommended` ("Rek. pris" — the manufacturer's RRP) and `packageContentSum` ("Utan paketpris" — a gift set's parts bought separately) are excluded on evidence:** across 24 products on one live listing, the first two appeared if and only if Lyko rendered the product as discounted (`useDiscountStyling`/`discountPercent` set) while every `recommended`/`packageContentSum` sat on an undiscounted product — treating an RRP as ordinarie would mark those permanently on sale and fill Erbjudanden with deals that are not deals. When several types qualify the LOWEST wins (a smaller claimed saving is the safer error; the ranking runs on what you pay either way), and an ordinarie at or below the current price is refused outright — the v0.32.1 invariant. **Lyko prints no jämförpris anywhere** (`unitPrice` null on all 24, no "Jämförpris" text on the site), so `store_unit_price_sek` stays None and the computed kr/unit is the only comparison figure — which is why the structured `size`/`unit` ("500 ml" as 500.0 + "ml") matter: package evidence with no title regex, and **deliberately no title fallback**, because a gift set named "Hand Soap A 300 ml & Hand Soap B 300 ml" carries `size: null` and parsing it would read 300 ml for 600 ml of product. **Identity is the URL's LAST path segment against the state's `canonicalUrl`**, not a trailing article code (a Lyko URL is a pure slug) and not the whole path — the same product answers on both a brand path and a category path with `canonicalUrl` pointing at the former, so comparing paths would refuse a page that is fine. A slug matching only a sibling in `variants` is refused: size variants have their own price. **`variantStoreAvailabilityStatus` must never decide stock** — it read "outOfStockInAllStores" on a product in stock and on sale online, because it describes the physical shops; `in_stock` comes from the schema.org availability in the state's own `linkingData` — **judged against the full JsonLdExtractor marker set (`OutOfStock`/`SoldOut`/`Discontinued`, v0.41.2)**, because this tier outranks JSON-LD in the ladder and a narrower check here means the stricter shared judgement never runs — falling back to `onlineStatus.interactionType`.

- **ICA is read from `window.__QUERY_INITIAL_STATE__`, and an ICA promotion is a LABEL, not a price (v0.43.0):** ICA (handlaprivatkund.ica.se) server-renders a JSON-LD node that carries ONLY the current per-unit price — a campaign lives solely in the react-query hydration state's `promotions` list (found live 2026-08-03: JätteFranska at ICA Maxi Sandviken, JSON-LD 27.30 with no offer while the page showed "2 för 45 kr"), and the printed jämförpris (`unitPrice`, "24,82 kr/kg") is likewise absent from JSON-LD. So `domain/extractors/ica.py` reads the state: `price.amount` → `price_sek` (ICA keeps it at ordinarie during a campaign, verified under the live one — so history was always right and only offers were missed), `unitPrice.price.amount` → `store_unit_price_sek`, `available` → in-stock, `packSizeDescription` ("1.1kg") → package evidence via `parse_package_from_name`. **Unlike Willys' API a promotion carries NO price field** — only the label text plus `requiredProductQuantity` — so the per-unit offer is PARSED from the store's own words under the v0.41.2 doctrine: "N för X kr" must agree with `requiredProductQuantity` (contradiction → refused), a multi-buy quantity whose label doesn't parse gets NO offer (never arithmetic), a label stating a SAVING ("Spara 5 kr", "%… rabatt") is never a price (5.00 would pass the inversion guard — it needs its own), **a label priced per MEASURE ("109 kr/kg" on a catchweight — v0.43.1, found live on kycklinglårfilé) is converted to the package via the store's own ordinarie/jämförpris ratio** (109 × 150.91/163.15 = 100.82 — the same arithmetic ICA prints the ca-price with; the bare 109.00 passes the inversion guard while wrong by the package weight) and only when the label's measure IS the jämförpris measure ("kr/st" needs no conversion — styck is the package, verified on a 200 g tomato tray and a 20-pack cola whose label is a truncated "90 kr/"; mismatch, missing jämförpris, or a multi-buy/min-quantity condition on a per-measure label → refused), quantization is öre half-up, several parseable promotions pick the HIGHEST per-unit (smaller claimed saving, Lyko's rule), and an offer ≥ ordinarie is refused wholesale with type+details (v0.32.1). `offer_details` carries the label verbatim so the multi-buy condition is visible; a label containing "stammis" gets `offer_type="stammispris"` (member price — the household is a member, so it still ranks). **Identity is `retailerProductId` against the URL's trailing digits** — the state can carry OTHER products (alternatives/recommendations), so a walk without that match returns None rather than a foreign price at 0.98 confidence. `extract_metadata_from_html` is deliberately None: ICA's JSON-LD already carries name/brand/size, so quick-add's JSON-LD tier previews everything. Every parse failure degrades to JSON-LD (right ordinarie, no offer) — treat "ICA-kampanj not flagged" as "the state changed shape" and check the `ICA promotion … did not parse` / `ICA state carries no product` WARNINGs.

- **An ICA e-handel offer is not proof of a shelf price, and `presentationMode` is the only hint we have (v0.60.0).** Until now the tracker treated ICA's e-handel as a faithful mirror of the butik, and for a year it was. On **2026-09-04** it was not: a buy-list row was driven to and did not exist at the till, and the staff said the offer was online only. The state's promotion carries more than the two fields the extractor read — `promoId`, `retailerPromotionId`, `type` and **`presentationMode` ∈ {DEFAULT, MUTE_STYLE}** — and MUTE_STYLE is the value that has never yet coincided with an offer in the butik's own veckoblad. **The measurement, and its limits, both matter.** Both Sandviken butiker's public erbjudandesidor were read the same day (`www.ica.se/erbjudanden/<butik-slug>-<id>/`, server-rendered `window.__INITIAL_DATA__` → `offers.weeklyOffers[]`, 187 at Maxi and 48 at Björksätra, each offer carrying name/brand/`mechanicInfo`/`validTo`/**EAN list** and per butik **`storeInd`/`onlineInd`**): of the six offers the tracker held, the four MUTE_STYLE ones were absent from the veckoblad and the one present in it was DEFAULT. A second, independent signal agrees — across all 26 ICA offers ever recorded, 22 lived 0–7 days (the veckoblad's own cadence) and the only four that lived 11–31 days are exactly those four. **But n is six offers on one day, and the inverse does NOT hold:** one DEFAULT offer (Arla Köket smör- & rapsolja) was absent from the veckoblad too, because the blad is the butik's ADVERTISED campaigns and not its whole shelf. So `domain/result.offer_online_only` is **THE** reader of the recorded flag and it answers three states — True (flagged), False (a mode was recorded and it was not MUTE_STYLE), **None (unknown, and the normal answer everywhere else)** — and False and None are deliberately not collapsed: "nobody said" is not "the store said this is a normal offer". Consumers MARK a True in the portal row, the buy-list mail and MCP with one wording ("kan gälla endast e-handeln") and say nothing on the other two. **It cannot be backfilled** — a promotion that has ended is gone from the page — which is why the flag was recorded in the same release that judges it rather than after more evidence.

  **The flag is INCOMPLETE, and this was established hours after it shipped — corrected here in place rather than appended as a contradiction.** The row that actually sent someone to the shop and was not there (Arla Köket smör- & rapsolja 7,5dl, ICA Maxi, "30 kr/st", staff: online only) carries `presentationMode: DEFAULT`. So MUTE_STYLE still implies "absent from the veckoblad" on all evidence so far, but a DEFAULT campaign can be online-only too, and **an unmarked row promises nothing** — which is what the three-state reader and the mark-never-filter rule already say, and now say for a measured reason rather than a cautious one.

  **The exact signal is `retailerPromotionId`, and it is already recorded (v0.60.0) though nothing reads it yet.** Its FIRST segment is the id of the corresponding offer on the butik's own erbjudandesida — `5004133591-1787037115` on the makaroner promotion is `weeklyOffers[].id` `5004133591`, the Kungsörnen row valid to 2026-09-06 — so leaflet membership is an **exact join, not a name match**: 6/6 on the 2026-09-04 sample (the one in-blad offer joined, the five absent ones did not, including the rapsolja `presentationMode` misses). Note the shortcut that does NOT work: the id prefix is not the signal, because both butiker's veckoblad carry `200…`-prefixed offers of their own (`2005267735` at Maxi, `2005258771` at Björksätra) — membership in the fetched set is the test, and only that.

  **The cross-check is therefore a DECISION about a new external source, not a rename, and it is unbuilt as of 2026-09-04.** `www.ica.se/erbjudanden/<butik-slug>-<id>/` is public, sessionless and server-rendered (`window.__INITIAL_DATA__` → `offers.weeklyOffers[]`), and it would also give `validTo` and the butiksunika offers e-handeln can never show us (2 of Maxi's 187). What it costs: one fetch per butik per check day at `www.ica.se` (a different host than handlaprivatkund, same WAF family — it must ride the shared ledger keyed `host:www.ica.se` and the breaker, like the Willys API does), a per-butik leaflet URL as operator config (the slug is not derivable from the handlaprivatkund URL, and at two butiker a table beats discovery), and a decision about where the verdict is written — at CHECK time into `raw_data` beside the id, so the mail and the portal read one stored answer instead of fetching at read time. The earlier reason for deferring it — "we store no EANs, so it would be the Willys-blad token-overlap problem again" — was WRONG and is retracted: the join is exact.

- **The veckoblad cross-check: an exact join, answered at CHECK time, and every failure is UNKNOWN (v0.61.0).** Built the day after the flag above, because that flag would not have caught the row that sent someone to the shop. `domain/ica_leaflet.py` is the pure half — `parse_leaflet` (the page's `window.__INITIAL_DATA__` → `offers.weeklyOffers[]`), `promotion_leaflet_id` (THE join key: `5004133591-1787037115` → `5004133591`) and the per-butik URL table — and `infra/ica_leaflet.py` is the half that fetches. Five rules, each of which fails silently if broken:
  - **The page is a JS object literal, not JSON.** It carries `undefined` and `new Map([])`, and they are patched **at the exact position the decoder stops**, never with a sweeping regex — `undefined` inside a product name or a disclaimer parses fine as part of that string, and rewriting it would corrupt a row rather than raise. An unknown literal ends the decode as unknown. Gated by a test that puts the word inside an offer's name.
  - **An EMPTY leaflet is UNKNOWN, not "nothing is advertised".** Both butiker advertise constantly (187 and 48 on 2026-09-04), so an empty array means a changed shape or a page that never hydrated. Answering `{}` would stamp every one of that butik's campaigns as absent from a veckoblad nobody read — the confident-wrong-answer failure this whole feature exists to prevent. The same holds for a wall, a timeout, an unconfigured butik and a raising lookup: all None, and `annotate_extraction` then writes NO key at all rather than a verdict.
  - **The verdict is written at CHECK time into `raw_data`** (`offer_in_leaflet`, `offer_leaflet_valid_to`, `offer_leaflet_store_ind`), so the mail and the portal read one stored answer instead of fetching per page load, and a row keeps saying what was true the morning it was recorded. It rides the shared ledger and breaker keyed **`host:www.ica.se`** — a different host from handlaprivatkund.ica.se, so a wall on one is no evidence about the other in either direction — and is cached per butik per **Swedish civil day** (a failure for 15 minutes only, so one bad minute cannot blind the day). 44 due ICA links cost ONE request.
  - **`result.channel_note` is THE sentence, and the deal row DERIVES it** (a property, not a stored field). Precedence: the butik's own `storeInd: false` → "butiken anger att erbjudandet inte gäller i butiken"; absent from the leaflet → "finns inte i butikens veckoblad — kan gälla endast e-handeln"; present → "finns i butikens veckoblad t.o.m. 6/9" (the butik's own date — the positive case is what makes the silence on other rows trustworthy); no leaflet answer → v0.60.0's weaker `presentationMode` hint; otherwise nothing. **It is a property because a stored note let a hand-built row carry the flags with no sentence** — the notifier's own fixtures went quiet exactly that way the first time this was written, and no runtime test outside those fixtures would have shown it.
  - **`perform_price_check` takes `leaflet=` and an AST gate requires it at every call site in `src/`** — the attempt_log shape, for the attempt_log reason: the default must be None (hundreds of tests drive the flow with mocks), so the default cannot be the enforcement. A caller that forgets does not degrade the buy list, it silently stops saying which rows the butik never advertised.
  
  **Config:** `ICA_LEAFLET_URLS` (JSON butik id → erbjudandesida URL), Magnus's two butiker as in-repo defaults, and **an entry that does not point at `https://www.ica.se/` is DROPPED with a warning** — this table is the only place a URL enters a scheduled outgoing request, so an operator typo fails closed. The slug is not derivable from the handlaprivatkund URL, which is why it is a table rather than discovery. **Still unread:** `onlineInd: false` marks the butiksunika offers e-handeln can never show us (2 of Maxi's 187) — the leaflet is now parsed and they are visible, but nothing surfaces them yet.

- **JYSK's JSON-LD hides the PRODUCT as well as the campaign, and that is why this tier owns identity (v0.57.0):** JYSK (Drupal + React SSR, `jysk.se` apex, `store_type="retail"`, interval mode at the 72h default) fails the generic tier twice over — both verified live 2026-08-16, both silent. (1) **A multi-variant product publishes `ProductGroup`, not `Product`:** the 24 NORA towel variants hang off `hasVariant`, which `JsonLdExtractor._find_product_node` never descends into (it walks `mainEntity`/`@graph` only), so the pasted URL returned None and every such page fell to the LLM. (2) **The published price is what one piece costs TODAY, never the ordinarie:** Badrumsmatta SANDHEM publishes 75 under a −50 % sticker while the page prints "Ordinarie pris: 149:- /st." — the generic tier recorded 75 as `price_sek`, the ordinarie/offer inversion v0.25.2/v0.32.1 exist to stop, which hides the campaign AND drops a campaign price into the 84-day floor as a normal shelf price. So `domain/extractors/jysk.py` resolves the variant first: **identity is the URL's `?article=` against the variant `sku`**, and an article absent from the group is REFUSED rather than answered with a sibling (the ICA `retailerProductId` rule). A bare path (no query) falls back to `hasVariant[0]` — JYSK publishes the path's own variant first, and it is the only one carrying a full name ("Badlakan NORA 100x150 sand"; the siblings are named bare after the group) — but that pick is only trusted when the page's PRINTED piece price agrees with it. **Identity needs one strong signal: the article anchor or the printed-price agreement. With neither, the extractor refuses**, because a wrong variant at 0.97 confidence is worse than falling through. Three price shapes, all in stable markup: plain (`product-price-value`), rea (`product-price discountprice` + `product-price-cheapest-price-notice` → "Ordinarie pris") and **flerköp, which is a LABEL not a price field** — `product-price-value` holds "2 för 369:-" while the piece price moves to `singlepieceprice`, so the per-unit offer is parsed from the store's own words under the ICA doctrine (currency marker required so "3 för 2" cannot become a 0,67 kr floor; öre half-up; `offer_details` carries the label verbatim as the villkor; refused when it is not below the piece price). **"Lägsta pris 30 dagar" is NOT an ordinarie** — it is the EU-Omnibus disclosure about a window, and reading it as one would invent a campaign every time the two lines differ. Three deliberate omissions: **no jämförpris** (JYSK prints only "/st.", so the computed kr/enhet is the sole comparison figure — Lyko's situation), **no package data** (`size`/`hasMeasurement` are DIMENSIONS, "100x150" cm, and `weight` is a fabric density in g/m² — parsing either would put 100 cm on a towel sold per styck), and **no real stock signal**: JYSK publishes no schema.org `availability` anywhere and the buy button is client-rendered, so `in_stock=True` is an ABSENCE, not an observation. `drupal-settings`' `productStatus` tempts and must be left alone — it is a LIFECYCLE code (the SANDHEM rea page read "21", discontinued, while selling fine), which is Lyko's `variantStoreAvailabilityStatus` trap again. `extract_metadata_from_html` IS implemented here, unlike Clas Ohlson's: the generic tier cannot preview a `ProductGroup` at all, so quick-add would otherwise hit the LLM for exactly the multi-variant pages this store is full of. Every parse failure degrades to JSON-LD (right price outside a campaign, on single-variant pages only) — treat "JYSK rea not flagged" as "the price markup changed shape" and check the `JYSK printed piece price … disagrees` / `JYSK article … is not among the` WARNINGs. NB one duplicate-link trap that is JYSK's own: the same variant answers on the canonical path, on that path with `?article=`, AND on `/articlelookup?article=N` (which 302s to the canonical) — `store_url` is the natural key with no normalisation, so all three are separate links.

*From the release index, removed by the information-layout move:* ICA's `_MULTI_BUY_RE` requires a currency marker, and a parsed per-unit offer must be at least 20 % of the ordinarie (v0.49.1 — "3 för 2" had parsed as 0,67 kr and stood as the floor for 84 days). Willys parses group separators in its numbers (v0.50.0). The LD-JSON block regex shared by the store-HTML extractors is `LDJSON_BLOCK_RE` in `extractors/base.py` (v0.57.0; it had grown two copies).

## Quick-add

**Quick-add (v0.5.0):** `POST /quick-add/preview` + `POST /quick-add` create a product AND its store link from one pasted URL (store matched by hostname, package parsed from the title). **The preview's identity ladder mirrors the price-check ladder: store API → store page-state → JSON-LD (v0.25.1; page-state tier v0.31.0; the LLM step removed v0.66.0 — nothing found leaves the form empty for the operator, and a store saying the product is gone answers 404 "Produkten finns inte hos butiken (…)" instead of previewing a sibling).** For a store with a structured API — `domain.parser.get_api_extractor`, currently only Willys — it reads identity + package straight off the REST API (`WillysApiExtractor.extract_metadata`) and never fetches the page. That tier exists because **Willys is a client-rendered SPA: its product HTML carries no JSON-LD and no price**, so the HTML→LLM ladder saw an empty shell and returned a blank form. A store in `get_html_extractor` (Rusta, Lyko and JYSK; Clas Ohlson and ICA are registered there but return None for metadata — their JSON-LD already carries what the preview needs, while JYSK's `ProductGroup` is invisible to the JSON-LD tier entirely) gets its identity from the fetched page's hydration state instead (`extract_metadata_from_html`) — Rusta's JSON-LD names are bare ("Deo roll-on Nivea") while CURRENT_PAGE's `subTitle` carries the package text the preview form wants prefilled, and Lyko's `entryName` is already the abstract good with brand AND size stripped ("Hand Wash Refill Milk & Honey" out of "Palmolive Hand Wash Refill Milk & Honey 500 ml") with `size`/`unit` giving the package as numbers. The pharmacies still take the JSON-LD path — verified 2026-07-26 that all five serve a parseable Product node server-side. The suggested name is the abstract good — `strip_brand_from_name` drops a leading/trailing brand the source folded in (v0.22.0), so it doesn't double-print beside the brand column. Preview-then-confirm on purpose — the confirm step is where "ny produkt" vs "ny länk på befintlig produkt" gets decided, which keeps quick-add from rebuilding the pre-04.1 one-product-per-pack-size shape. **A duplicate URL is refused BEFORE the fetch, and since v0.56.2 the refusal leads somewhere:** the preview short-circuits with `already_tracked`, which carries `product_id` and not just the name, so the product name in "URL:en bevakas redan" is a button into that product's links panel — the same destination Fel & luckor's rows resolve to, because that is where a link's real actions live. It closes quick-add FIRST: the panel would otherwise open beneath a dialog still on screen (the stacking order is built for the reverse — `#modal-link-store` sits above the panel). **The mängd is DROPPED when the canonical unit changes, and `pkgRekeyUnit` is the one place that does it (v0.58.1).** `pkgInitChain` takes the amount as an argument, so the two call sites that read the field back and re-key it — `qaUnitChanged` (Enhet changed on a new product) and `qaProductChoiceChanged` (attached to an existing product with another unit) — carried 0,27, parsed as kg out of a "…270g" title, into a product counted in `st`, where it means 0,27 STYCK. `pkgFieldsChanged` then sets `step="1"` (a count is whole) and the browser refuses to submit with "the two nearest valid values are 0 and 1" — v0.53.3's shape again: a correct rule delivered as an unreadable message. Nothing wrong reaches the DB; what breaks is the normal path for a one-size product, where the title says 270 g and the product compares per styck. **An operator-written LABEL survives** ("270 g" describes the package truthfully whatever unit it is compared in, and `package_size` never enters arithmetic) while an auto-suggested one goes with the amount that generated it — `labelDirty` is carried across, not re-derived, or an auto-label would latch merely by surviving. **A no-op when the unit is unchanged**, which also stops an unrelated re-render from snapping the operator's entry-unit choice (g, ml) back to the canonical first button. No runtime test can see any of this — the form errors in the browser and the API is never reached — so BOTH call sites are gated in `test_static_gates.py`.

Decision logic is pure functions in `domain/quickadd.py`; full design in `docs/quick-add.md`.
